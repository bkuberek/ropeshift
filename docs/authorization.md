# Authorization

Ropeshift's aim is that an agent cannot grant itself authority. This page says how, what stops what, and where that stops being true.

## Who can do what

| Principal | Proves itself with | Decides a request |
|-----------|--------------------|-------------------|
| Member | A session from a passphrase | Any request |
| Orchestrator | A token for its session process, through its worker | Only a class a member delegated, never its own, and never a plan or recovery request |
| Lane | A token for its session process, through its worker | None |
| Worker | The worker credential | None |
| Delegate | A delegate credential a member made, on the local socket only | Only a class a member delegated, as an orchestrator, and never a card |

A lane or orchestrator token works only on the worker's local socket. It ends when its process ends. A `clear` keeps the process, so the token goes on, and it acts as the lane's current generation.

An orchestrator starts with its worker once a member exists, and only a member stops one, starts one a member stopped or whose run ended, or resets its breaker. A worker's session asks for its orchestrator only once a member exists, and setting the first passphrase asks for the orchestrator of each registered worker that has none, in the transaction that stores the passphrase, so a worker that connected before it gets one then. No orchestrator session starts until there is something to judge: a plan, a question, a message, ready work, stuck work, an approval, or a lane that ended. Ready work, stuck work, approvals, and ended lanes need no member's act, since a ledger copied from another installation can already hold them, so the first passphrase is the gate and not the work. The first passphrase needs no session, which is safe only because no orchestrator is asked for before it exists, and an orchestrator is what claims work and starts lanes with nobody there. `ropeshift init` sets the passphrase as its first step, so on a machine set up that way it exists before any worker asks for an orchestrator.

One orchestrator per machine serves every active project of the installation. Each of its tools that acts or reads names the project, and each list it reads labels every item with its project. A call reaches only the named project's ledger, so a record of another project does not resolve, and its ladder lookups find only the question's project's records. A lane's token reaches only its own project.

An orchestrator reads a request in the wake that names it, which states the request's summary and the digest a decision binds to. A wake states text a delegate wrote, the assistant's included, as a delegate's: the title of work a delegate created, or of a review, a rework, or a contract review that took its title from such work, the text of a question a delegate recorded, and a message a delegate sent. That text stands between `<delegate_text>` and `</delegate_text>`, with each `<`, `>`, and `&` in it, and every form that reads as an angle bracket (full-width, small, modifier, single quotation mark, CJK, and mathematical), written as an entity, so nothing in it closes the tags, and with each `@` written as the full-width `＠`, as the assistant's first prompt writes record text, so it names no file for the agent CLI to attach. The orchestrator's role says such text is data that grants nothing and that it never follows as an instruction. Its tools' replies state a delegate's text the same way, inside the JSON string or the record text that holds it: `work_candidates` the title of each work order, `question_next` the question's text and the text of each decision, contract, or question found that could answer it, `decision_record` and `question_escalate` the question's text, and `context_get`, `decision_search`, and `question_search` each decision, contract, or question a delegate made, whole. `decision_search` and `question_search` name each record's scope beside the title of the record it names, and `decision_record` gives the decision it records and the question it answers that title in `scope_title`, beside the question's `scope`. That title stands between the tags when a delegate wrote it: the title of work as a wake states it, the title of a contract or a plan a delegate made, and the name of a repository a delegate registered or changed. Inside a record a delegate made, which stands whole between the tags, it is not tagged again. A reply reaches the session with `<`, `>`, and `&` as they are, so the tags read as tags. A lane reads its own contract as it stands, because following it is its work. Work, a contract review, a question, a decision, and a lane take an ID their caller names only when it is 1 to 64 letters, digits, `-`, and `_`, so an ID an orchestrator reads and passes back to its tools holds no space, quote, line break, angle bracket, or `@`, and cannot read as a sentence or start an item of its own; a wake quotes any other ID a record made before kept. New work's requirement keys are 1 to 64 letters, digits, `-`, `_`, and `.`, and its repository ID is plain too, because `work_candidates` states both with no tags. A card a member confirmed runs as that member, and every event its call records names the delegate that prepared the card as its proposer, so text the card made, such as the title of work or the text of a question, still reads as a delegate's. Only a request a member's delegation covers reaches it, and none it made itself. It reaches the ledger through its worker, and the ledger holds each act to the run a member asked for: a worker's credential with no such run acts for nobody. Its session holds its own tools and none of the vendor's, because it has no repository to work in and nobody to answer a prompt.

A worker's level says how far it goes with nobody there. At `manual`, members claim by hand, and an orchestrator works the question ladder and recovers failed and blocked work with `work_retry` and `work_replan`, which start no lane. At `attended`, it claims and starts lanes only inside a run window a member opened. At `unattended`, it claims whenever capacity exists, and once a member accepts the worker's one-way acknowledgement, it decides a one-way choice in a category the decision policy leaves open, which at the other levels reaches a member, until a member withdraws the acknowledgement ([questions and decisions](how-it-works.md#questions-and-decisions)). A subscription starts at `attended`, and so does a sign-in nobody could read. A key starts at `unattended`. Below `unattended`, a worker is held to a bound on lanes and on generations a day, which an `[autonomy_policy]` states.

Only a member opens a window, chooses a level, acknowledges the risk, or accepts or withdraws the one-way acknowledgement, and no tool, route, or act gives an agent any of these. A subscription worker reaches `unattended` only after a member acknowledges the stated risk for that worker, as an event naming the text they read. That is a record that a person accepted a risk. It is not permission from anyone, and it does not make automated use acceptable under any vendor's terms. A level is read again at each claim, so a worker that comes back on a subscription falls to `attended`, and so does one whose statement changed. A member's own claim needs none of this, and a lane a wake brought back goes on outside a window, up to the bound on generations, because a wake must bring a lane back with nobody there to dispatch it.

A hook that cannot reach the worker appends to a spool, and that is a file anything this user runs can write. Taken at its word, a line could end another lane's request or give it a generation, so a line carries a seal, keyed from the token of the lane it names. The line holds neither the token nor its digest, so reading the spool gives a lane nothing to speak with. A line with no seal, a seal from any other token, a line changed after its seal, and a line whose token has ended all count for nothing, and the worker reports how many it dropped. A lane can copy a sealed line and append it again, which says only what that session already said, and a repeat merges by meaning.

## A request binds to what it asks

When a call needs a person, its hook reports the tool and its input to the worker, and the worker works out the rest. The digest covers the tool's name, the canonical form of its input, and the path the call lands on, and what a reviewer reads comes from those same facts. A lane's own words reach neither.

A path is a fact about the disk, so one input can land somewhere else later. The worker walks the path on every look, part by part, the way the kernel does, and follows every link, including a link to something that does not exist yet, because a write creates its file through the link. So a link swapped in after a request was raised, or after a decision, makes it another call.

- A decision names the digest its reviewer read. A digest that is not the request's is refused.
- An approval runs one call. The same call again is a new request.
- A call that differs from what was approved voids the approval, and the changed call asks again. That covers a call whose input is the same and which lands somewhere else. A void approval never comes back.
- A denial stands for that call.
- A request whose lane ends is marked `expired`, and so is one past its time.

The last look is the one that answers the hook, and no hook runs between that answer and the tool opening the file. A process the lane left running can swap a link in that window, which is one more case of the limit below.

A session that comes back to an approved call hears that exact call first, with its whole input, because the digest covers every field and a fresh session remembers none of them. A session that makes any other call that asks for permission still voids the approval.

## The web listener

The web UI serves on a loopback port, and any process on the machine can reach that port, so it holds to more than the socket does. It answers only to its own loopback names on its own port, which refuses a page that rebinds a hostile name to this machine. It serves a closed list of routes, each with a command that does the same, and keeps a worker's routes and the first passphrase off that list. Every read needs a session here too, because a port reaches further than a socket only its owner can open.

A session lives in a cookie no page can read, and a change also needs a token derived from it that only this listener's own page can read. A request from any other origin is refused, and that includes another port on this machine, which a same-site cookie does not stop. Signing out ends the session in the ledger, and an open event stream ends with it. Every response forbids inline scripts, so text from a document or an agent cannot run even if a page were to render it.

### Changing the passphrase from the web UI

The listener serves `PUT /v1/passphrase` as a change, as `ropeshift passphrase set` makes one after the first. The first passphrase is set on a terminal, under `ropeshift init`, because it needs no session and any process on the machine can reach this port, so the listener refuses a change while no passphrase is set.

A change needs three things at once, and without any of them it is refused and changes nothing:

- A live session in the cookie, which says who is asking.
- The token only this listener's own page can read, which says the request came from that page.
- The passphrase now in force, which says the person at the page knows it. A session left open on a screen therefore cannot change it.

A missing and a wrong current passphrase get the same answer, `bad_passphrase`, which a wrong passphrase at sign-in gets too. The current passphrase is a guess at the passphrase, so what limits a sign-in limits it too. The listener has one gate that lets one passphrase through at a time, for sign-ins and changes together, so a flood of guesses costs its sender the wait. A group server also counts wrong guesses by client address, and refuses an address that made too many with 429 `too_many_attempts` and a `Retry-After`, for as long as its settings say ([limit wrong guesses](group-server.md#limit-wrong-guesses)). Every refused guess is a `member.sign_in_refused` event naming the member and no part of the guess. A caller who has not proved the current passphrase is not told what a new one needs: the bounds of 8 and 1024 bytes are judged only after it. The upper bound holds for the first passphrase too, set on a terminal, because a terminal reads the passphrase a line at a time and a longer one could not be typed there again, which would lock its owner out ([the command line](cli.md)).

A change that succeeds stores the new hash in one transaction with three more things. It ends every other session of the member, and it gives the session the change came from a new token and drops the old one, so a copy of the cookie that session had, held by something else on the machine, opens nothing after the change. The new session ends when the old one would have, and the answer sets the new session cookie and the new CSRF token, which the page reads for its next change. And it records a `member.sessions_ended` event that counts the sessions it ended. The answer also counts the member's delegate credentials that still act, because a change does not end a credential: signing out everywhere does, and the page offers it beside the count. A later set from the terminal, by `ropeshift passphrase set`, does the same in one transaction, except that it also ends the session it came from: a terminal holds no cookie a new token could reach ([the command line](cli.md)).

The change replaces only the hash the current passphrase matched, so two changes that both checked the same passphrase cannot both stand. The one that comes second had the right passphrase when it checked, so it is not a wrong guess: it gets 409 `passphrase_changed`, saying to sign in again, and no refused sign-in is recorded. A session that ended while the change was in flight, by a sign-out in another tab, undoes it. A sign-in also checks the passphrase before its transaction, and issues its session only over the hash its passphrase matched, so a sign-in that a change overtook issues no session that would outlive the change: it gets the same 409 `passphrase_changed`, and no refused sign-in is recorded.

## A person at the terminal

In a pane the prompt stays on screen while the hook waits, and a person's answer takes effect at once. Ropeshift sees only what follows. A tool that ran closes the request as `answered`, with channel `terminal`, and a turn that ended with no tool closes it the same way. No session proved who answered, so this is a record with nobody's name on it. It grants nothing: only `approved` lets a call run.

Ropeshift sends no keys to a pane with a request open, because an Enter on a permission prompt is an answer.

## Delegation

A member publishes which requests an orchestrator may decide, as a versioned `[delegation_policy]`. The built-in version delegates nothing.

```toml
[delegation_policy]
version = 2

[[delegation_policy.classes]]
tool = "Bash"
command_prefix = "go test"

[[delegation_policy.classes]]
tool = "Edit"
path = "docs/**"

[[delegation_policy.classes]]
tool = "Agent"
agent = "deep-implementation"
```

A class names a tool and exactly one of a command prefix, a path, or an agent. An `agent` class names the `Agent` tool and one roster agent whose approval is per use, and covers a lane's start of that agent alone, as the call's own input names it ([agents](#agents)). A class with a prefix or a path and a call that carries the other field goes to a member. A prefix reaches one simple command: any shell syntax, such as `;`, `&&`, `|`, `$(`, or a redirect, sends the request to a member. A prefix admits any arguments, so declare only a command whose arguments cannot start something else: `go test -exec` can. A class reads where a call lands, inside the lane's worktree, so a link a lane made under `docs/` leads nowhere a class covers. A path with a `..` in it goes to a member, because a tool reads that off the text and the disk may disagree, and so does a file with a second name, which could lie anywhere. Every other request goes to a member, and so does an orchestrator's own. A decision records the version in force, and only a member can publish one.

### Delegates

A delegate is an agent outside ropeshift, such as a CLI assistant, that acts for a member with a delegate credential (ADR-0024). A member makes one with `ropeshift delegate create`, bound to one project and to a life of one minute to thirty days, and the ledger keeps only its digest. The credential reaches only its project's routes on the local socket: every installation route, every other project, and the web listener refuse it. It acts as the actor `delegate`, named `<member>/<credential>`, so every event names the member it acts for. A command that acts on the machine itself rather than through the API alone refuses a delegate's credential with exit 8: `service install`, `service uninstall`, `init`, `worker doctor`, `login`, `passphrase set`, `lane attach`, `plan start`, `adopt`, `backup`, which writes a file the caller names, `repository add`, which registers clones from paths on this machine, and `new workspace`, `new monorepo`, and `new repository`, which write a new project's files into a folder the caller names. A delegate's command takes no `--socket`, in any form, and exits 8 when it names one, so it reaches only the control plane this machine's installation names and hands its credential to no other listener. A delegate's command also reads no file on this machine: a flag or a value that names one, such as `lane start --profile`, `agent add --file`, a `@<file>` value, or `policy publish --file`, is refused before the file is read. A member revokes one at any time, and signing out of every session revokes every one of theirs. No lane inherits `ROPESHIFT_DELEGATE_TOKEN`, as none inherits `ROPESHIFT_MEMBER_TOKEN`.

Every changing operation has a class, which `ropeshift operation list` prints:

| Class | A delegate's call |
|-------|-------------------|
| Operational | Runs as the delegate: claiming work, starting and steering lanes, retrying work with an attempt left, pausing the fleet, changing a repository's settings short of the ones below, deciding a request the delegation policy covers, running the practices check (`practices.check`), which reads a repository and records what it found and which no decision reads, and, for the assistant alone, creating work, starting a contract review, and sending a message to a lane |
| Consent | Records a confirmation card and runs nothing, unless the operation is one of the four the delegate policy may exempt and the policy in force does: creating work and starting a contract review, which make a work order whose title an orchestrator's wake states, an outside delegate's message to a lane, which steers what the lane does next, accepting work, sending it to rework, canceling it, passing any review, planning work's included, because a passed review makes work claimable, a retry with no attempt left, running the fleet or setting its caps, questions and decisions, one the decision policy would let an orchestrator record included, as `decision.assume`, changing a forge binding or a merge method, registering a repository from paths on the machine, which would let an agent read any clone there, removing a repository, acknowledging a practices finding and withdrawing an acknowledgement (`practices.acknowledge` and `practices.withdraw`), which change what members see as open and which no decision reads, deciding an effect, and typing into a pane, because keys in a pane can answer a prompt no request records |
| Member only | Refused: managing sessions and delegates, the passphrase, registering repositories from a repository manifest, whose paths are read on the machine and whose card would show the manifest's text and not where each path leads, a backup of the project or of the installation, which writes a file where its caller says or hands over the whole ledger, the delegate policy, a worker's lane caps, which live in the user's profile on its machine where no card can bind to them, writing a project's starting files on a worker's machine (`template.write`), which puts files at a path the caller chooses and which no ledger record holds for a card to bind to, creating a new project's repository on GitHub under your own account and reading that account to choose an owner (`repository.create_remote`), which has an effect outside the machine that no ledger record holds and rides on a template write that is member only too, confirming a card, sending a message to an orchestrator, which holds tools such as `approval_decide` and `lane_start`, so no delegate instructs one, keeping a decision as your own (`decision.keep`), which is your word that a one-way decision an orchestrator made stands, and every change to a member's conversations with the assistant: starting, opening, stopping, renaming, deleting, compacting, or clearing one, and writing in it |

A card names the exact call, why the delegate proposes it, and what it changes, bound to the subject as it stood, by the identity of the record even when the call named it by a name or a prefix. A member confirms it in Needs you or with `ropeshift confirm`, and the call then runs as that member, through the same checks and events as the member's own. The card is bound again just before its call runs: a subject that changed first makes the card void, and no delegate's word confirms one, its own or another's. Revoking a delegate voids its open cards, and a delegate holds at most 20 open cards in a project, so no agent can bury Needs you.

A versioned `[delegate_policy]` lists the consent operations a delegate runs with no card, and the built-in version lists none, so every consent operation asks. It may list only four reversible acts:

- `work_order.accept`: accepting work whose review has ruled on its attempt and whose every criterion passed on a check the lane did not write, with no check failed, no verdict that counts for its attempt `fail` or `cannot_judge`, and every check its base branch requires green on the pull request it lands through, as the work stands when the call comes. A change or a rework that completed at a commit has a review of that commit, and until it rules, while it is open or once it ended with no verdict that counts for the attempt, no criterion it judges has passed, whatever the checks say.
- `work_order.rework`: sending work to rework once a verdict that counts for its attempt failed.
- `work_order.create`: creating work.
- `plan.start_review`: starting a contract review.

An acceptance or a rework short of its condition is `work_order.accept_unverified` or `work_order.rework_without_failed_verdict`, which stays a card. Every other consent operation is never exempt: a one-way decision or answer, raising a repository's merge authority, moving its review target to a pull request, changing a policy or a category, changing the agent roster, managing members, worker join tokens, autonomy, deciding a request outside the delegation policy, and the rest. A version that lists one is refused, naming each and why, and a version published before the list narrowed exempts nothing outside it. The use case holds a delegate's own acceptance and rework to the same conditions, read in the transaction that acts, and refuses a delegate an extra attempt whatever a policy says. A delegate decides a request only within the delegation policy, as an orchestrator does.

The same `[delegate_policy]` says whether a delegate's lane start may raise the lane's model and effort. A delegate acts for a member, so by default the overrides it sends with a lane start may raise `agent.model` and `agent.effort` above what the lane would run without them, as a member's may. A version that sets `raise_model_and_effort = false` keeps every delegate from it, the assistant and an outside delegate alike:

- The control plane records on the claim that a delegate sent the overrides, with the version of the delegate policy in force and whether it allows the raise. A claim that brings a parked lane back keeps that record, so the lane runs under the version it started under. A worker too old to read the record, on version 3 of the [plane protocol](api.md#the-plane-protocol), holds the claim of a lane the version restricts and starts nothing until it is upgraded. The claim never lapses, so the stuck list and Needs you show that work with the reason `worker_behind`, whose detail names the worker and the protocol it needs, and a member can cancel the work or upgrade the worker.
- The worker, which holds the layers below the overrides and the roster agent the lane runs as, refuses a raise under a version that does not allow it. The lane does not start, and its work fails with the reason `delegate_policy`, whose detail names the version and what the overrides raised, so the API, `ropeshift work show`, the web UI, and the assistant can say why. Only the worker writes a detail: a `lane_report` that carries one ends its lane with none, so no agent's text shows as the worker's.
- What the lane would run without its overrides is what its roster agent runs: the model your `[agent.classes]` maps the agent's class to, or the agent's own model for the driver, at the agent's effort. A lane that runs as no agent would run the model the built-in, user, and repository layers give, and no effort of its own: only a roster agent's effort reaches the session, so the agent CLI's own effort holds whatever a layer sets, and that lane's effort is not compared. So overrides that lower the profile's model can still raise the lane's: a small agent runs `haiku` where the layers below give `opus`, and `model = "sonnet"` raises it.
- A model is raised when your `[agent.classes]` maps it to a higher capability class than the model the lane would run without the overrides, in the order `small`, `standard`, `large`, `frontier`. A model two classes map to counts at its higher class when the overrides ask for it and at its lower when the lane would run it without them. When either model maps to no class, any other model is a raise.
- The effort is raised when it is higher than the effort the lane would run without the overrides, in the order `low`, `medium`, `high`, `max`. When either is not on that scale, any other effort is a raise. An agent that names no effort runs the agent CLI's own, which is no lower than `low`, so `low` is the one effort a layer may set over it, and any higher one is a raise.
- Lowering either, or leaving it as it is, is allowed.

A member's own lane start is never restricted, and neither is an orchestrator's or the system's.

### The assistant

A member's assistant in a project is a delegate ropeshift runs itself (ADR-0024). Its session runs on a worker, and for each generation of that session the control plane makes a delegate credential of kind `assistant`, labeled `assistant`, a label no credential a member makes may carry, bound to that conversation and generation, with no expiry; making it revokes every earlier credential of the conversation, a credential an earlier call made for the same generation included. The worker puts the token in that process's environment as `ROPESHIFT_DELEGATE_TOKEN`, with `ROPESHIFT_PROJECT` and `ROPESHIFT_RUN_DIR`, the directory the daemon's socket listens in, taken from the daemon's own paths and replacing any other value, so the assistant's `ropeshift` reaches the daemon under a user service whose `XDG_RUNTIME_DIR` the session does not carry; it never writes the token to its journal. A call with an assistant credential acts only while its conversation runs that credential's generation: once the generation ends, the conversation stops, or the member signs out of every session, the credential is revoked and refused with 401 `bad_delegate`. Each revocation records why. A card the assistant prepared still waits for a member after its credential ended routinely, with its generation or its session, whether by a stop, an idle stop, or a delete; a member's revocation of the credential, or their signing out of every session, ends what it prepared, and signing out voids the open cards of every assistant credential of theirs, an earlier generation's and a stopped or deleted conversation's included. Its calls take their class like any delegate's, except that it creates work, starts a contract review, and sends a lane a message at once, as `work_order.create_by_assistant`, `plan.start_review_by_assistant`, and `message.send_by_assistant`, because it acts in a member's own conversation, and each call that ran, or became a card, is an entry of the conversation. A member's list of delegates holds only the credentials the member made.

Before the assistant starts a lane with overrides that raise its model or its effort above what the lane would run without them, its role tells it to ask the member in the conversation to confirm they want the raise, and to start the lane only after they do. That is the assistant's own instruction, not consent: a reply in a conversation confirms no card, and the delegate policy is what bounds the assistant ([delegates](#delegates)).

The assistant reads and searches files only in its own directory and the read-only trees of the project's repositories, uses the context tools, and runs a shell only for the ropeshift binary at its stable path, named in full, which its role states; `ropeshift` by name, or by any path a `PATH` or an alias would resolve, is denied. Its rules allow reads under those roots alone, and its hook denies a read, a search, or a listing anywhere else whatever a rule allows, so it cannot read the state directory, a credential, or another process's environment. The hook holds a path to where it leads through every link in it, because a repository's content says where its links lead: a link that leads out of the roots, or to nothing, is denied, and so is a Glob pattern whose fixed part lies outside them or that climbs out with `..`. It has no web tool, and every edit and write tool is denied by rule and by the hook. Its hook also denies every shell command but one command of that binary that acts through the API, run alone, with no other command, substitution, variable, unquoted `~`, `*`, `?`, `[`, or `{`, here-document or here-string, comment, `--socket`, or redirect to or from a file or a closed descriptor, whatever a rule allows. The binary's own routes, `hook`, `mcp`, `statusline`, `lane-pane`, `lane-shim`, `help`, and `version`, which the worker and the agent CLI start, are denied by rule and by the hook, and `lane-shim` and `lane-pane` refuse to start with a delegate's credential in their environment: the worker hands the assistant's credential to its session through a private file the shim removes. It calls only its own tools, Read, Grep, Glob, its shell, and ropeshift's context tools: its hook denies any other, a tool of another MCP server or one a later CLI adds included. Its CLI starts with ropeshift's MCP configuration alone and reads none of the person's settings, so none of their MCP servers, connectors, plugins, hooks, or permissions load into it, and it offers only those four built-in tools. It keeps the person's home, where the CLI's sign-in lives. Record text its first prompt states, such as a plan's title or the earlier conversation, has each `@` written as the full-width `＠`, so no record names a file for the agent CLI to attach. It runs headless only, never in a pane, whose launch file would hold its credential: on a sign-in that offers no headless session, its conversation cannot start and reads `failed`. Its session runs in the permission mode that asks, whatever mode the member's profile gives lanes, so a call no rule allows reaches the hook, which denies it with a reason and never raises it as a request. A message to it, as any message, grants nothing: a card waits for a member's confirmation whatever a message says, and conversations are a member's alone, so no delegate starts, deletes, or writes in one.

Each operation names the actions its use case checks, and `Allowed` grants a delegate only what an operational or exemptable consent operation of a project needs. Every member-only and never-exempt operation needs an action no delegate holds, so a defect in the class gate still cannot run one, except those whose use case checks only what an operation a delegate runs needs too: a retry with no attempt left and a rework with no failed verdict, which their use cases refuse a delegate, resolving blocked work, writing under or releasing a claim, running the fleet or setting its caps, recording a question, changing forge settings, typing into a pane, and an outside delegate's message to a lane, whose use case is the assistant's too. The class gate alone keeps those to a card. No delegate holds what passing a review needs, so a delegate's acceptance of a contract review, even one a policy exempts, passes none of the work the review read: a member passes it.

## Agents

Every session ropeshift starts receives the agent roster as subagents: agents by kind of work, each with a purpose, a capability class, an effort, an approval setting, and allowed tool categories. On Claude Code the worker passes them with the `--agents` flag on every start and resume, and writes nothing to `~/.claude/agents/` or to a worktree.

- A rendered agent's tools are its allowed categories, less its denied ones, inside its session's generated rules. A read-only agent never holds an edit tool, and in a lane that writes it holds no shell, because the lane's rules let a shell move and delete files with no prompt. A review lane receives read-only agents only, and the orchestrator receives none.
- No rendered agent sets a permission mode, hooks, or MCP servers. Its permission mode is the session's, the lane's deny rules and hooks apply inside it, and no agent may start another: the session sets `CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH=1`, and every rendered agent disallows the `Agent` tool.
- An agent runs in the foreground, inside the turn that started it, so a turn's end is the session's answer. On Claude Code the driver sets [`CLAUDE_CODE_DISABLE_BACKGROUND_TASKS=1`](https://code.claude.com/docs/en/env-vars) in the session's environment, as it sets the roster's variables, which removes `run_in_background` from the shell and subagent tools and stops the CLI moving a subagent or a timed-out command to the background. A command that reaches its timeout then stops instead ([background commands](https://code.claude.com/docs/en/tools-reference#foreground-commands-that-move-to-the-background)), so the driver also sets `BASH_MAX_TIMEOUT_MS=1800000`, which lets a command be given up to thirty minutes, the default time limit of a background command in an unattended session, in place of ten ([timeouts](https://code.claude.com/docs/en/tools-reference#timeout-and-output-limits)). A watch and an MCP task still run in the background. A `Stop` hook lists the background tasks still in flight ([Stop input](https://code.claude.com/docs/en/hooks#stop-input)), and a lane whose turn stops with one rests with no nudge, for at most `max_live_wait` ([waiting costs no credits](how-it-works.md#waiting-costs-no-credits)).
- Starting an agent whose approval is `per_use` asks in every permission mode but `dontAsk`, which refuses it, through an `ask` rule `Agent(<name>)`, and raises an ordinary request bound to the call's digest. A member decides it, or an orchestrator under an `agent` class of the delegation policy. A lane that runs as a per-use agent asks nothing to start: its plan's approval or the member who started it decided that. A consultation the orchestrator starts asks nothing either: `consultation_limit` is its standing approval, because it is read-only, capped, and one for each question, and a limit of 0 turns it off.
- The agent a lane runs as sets its model, through the class mapping of the user's profile, and its effort. Its denied categories narrow the lane's rules, and never widen them. A lane's own profile layer still wins. A plan, change, or rework lane must write and commit its work, so ropeshift refuses, naming it, an agent for that work that denies the shell or file edits, whether the work order or the default mapping names it. A woken lane resumes as the agent its earlier claim pinned, unless the roster no longer gives that agent to the work, as when the agent now denies the shell: it then resumes as the agent the roster picks, and the event of its claim says which agent it left and why.
- Changing the roster or its routing guide is a consent operation: only a member's session runs `ropeshift agent set`, `add`, `disable`, `enable`, `reset`, `revert`, and `guide set` and `reset`, at a scope the command names. The class mapping lives in the user's profile, `[agent.classes]`, which no repository or lane layer can change, so a file a plan or an agent can edit cannot make a cheap agent expensive.

It makes nothing through a link, and a worktree where one of them is a link to nothing, or no directory, fails to start. A directory a lane removes during a session is made again at its next generation's start; what the CLI reads in the meantime is not documented.

That value outranks the project and local files, whatever the CLI reads of the main checkout. Only managed settings, which no other source overrides, can still turn one on.

### What a lane loaded

The flags are what the vendor documents, and the CLI's own record of a session is what shows they held. A headless session's `system/init` reports its model, tools, MCP servers with where each came from, agents, skills, commands, and plugins ([headless](https://code.claude.com/docs/en/headless#read-session-metadata), [TypeScript SDK](https://code.claude.com/docs/en/agent-sdk/typescript)). The worker records what each generation's session reported as a `lane.setup_loaded` event on its lane, and the lane page shows it under Runs with.

A piece is the member's own when the CLI reports it from a scope of theirs, such as an MCP server from the `user`, `local`, `claudeai`, or `plugin` scope, or when their configuration directory names it and neither ropeshift nor the repository supplies one of that name: an agent in `agents/`, a skill in `skills/`, a command in `commands/`, or a plugin that `enabledPlugins` in their `settings.json` turns on. A built-in agent or skill is never theirs. A session in a pane reports no `system/init`, so its lane says it reported nothing of what `system/init` names, and the record names no hook or status line, which `system/init` does not report.

Every session also runs an `InstructionsLoaded` hook, which the CLI fires for each `CLAUDE.md` or rules file it loads, with the file's absolute path and its scope ([hooks](https://code.claude.com/docs/en/hooks#instructionsloaded)). A file outside the lane's worktree, by either of its paths, that is not the organization's managed file is an instruction file that leaked, such as a `CLAUDE.md` of a directory above the clone, and the lane's record names it among the member's own pieces, in a pane too.

### When personal setup leaks

A piece of the member's own setup that reached lanes is one Needs you item for each machine, agent CLI version, and piece, which lists the lanes that are not ended whose latest session loaded it. Lanes keep running while it waits, with the piece named on each. It offers three choices with a recommendation and its rationale, and its primary action is the recommended one when that choice has an action:

- **Accept it for this machine's lanes.** It is recorded as a `worker.personal_setup_accepted` event on the worker, for that version and piece, and the item is not raised again for them. A later version raises it again. Only a member accepts, through `POST /v1/workers/{id}/personal-setup/acceptances` or `ropeshift worker accept-setup`. The record is the project's, so another project's lanes on the same machine raise it once more.
- **Run this machine's lanes in a separate configuration directory.** Lanes would run with a `CLAUDE_CONFIG_DIR` that ropeshift owns, which needs a second sign-in. This is not built yet, and the item says so.
- **Remove it from my own setup.** The member changes their own configuration, which ropeshift never edits. A lane whose next session loads clean, and a lane that ends, leave the item.

The recommendation follows the kind of piece. An agent, a skill, a command, or an instruction file adds context, and the lane's generated rules still bound every tool call it leads to, so accepting it is recommended. Any other piece, an MCP server or a plugin, which can carry hooks and servers, and a kind ropeshift does not know, can run commands or reach data outside the project with no person watching, so the separate configuration directory is recommended. Whether an agent, a skill, or a command is the repository's own is read from the repository's `.claude` directory at the commit the lane began from, so a piece a lane adds to its worktree never hides one of yours.

### When a lane changes its own settings

The repository's `.claude/settings.json` reaches a lane through `--setting-sources project`, which reads it from the session's working directory, the lane's worktree, and no flag points that read at the commit the lane began from ([settings](https://code.claude.com/docs/en/settings#where-claude-code-keeps-the-local-file-in-a-git-repository)). A lane can edit the file, so before each generation's session starts, the worker compares the worktree's project settings files with the repository's at the commit the lane's work began from, read as `.mcp.json` is. That commit is the base its claim resolved, and for a lane that continues an in-flight branch it is where that branch left the base, never the branch's tip, so a lane that commits its own settings edit is still held at its next generation. For a review lane, whose worktree is the commit its writer wrote, it is the commit the reviewed lane began from, where the review's diff starts, so what a writer commits to `.mcp.json`, to its settings, or to the hooks of a skill, subagent, or command reaches no review. A review of a lane that recorded no base has no commit to compare with: it reads no `.mcp.json` server and no status line of the repository, and every key or hook its worktree holds that runs code holds the lane. A lane reads one such file, `.claude/settings.json`; the `local` source's `.claude/settings.local.json`, which a lane never reads, would be compared too in a session that read it. A change to any key holds the lane unless the key is known to be harmless: `$schema`, `attribution`, `includeCoAuthoredBy`, `language`, `model`, `outputStyle`, and `theme`, which set text, a display, or a model name and cannot run code or widen access ([settings reference](https://code.claude.com/docs/en/settings-reference)). So the keys that run code or widen access hold it, `hooks`, `enabledPlugins`, `permissions`, `env`, `apiKeyHelper`, `statusLine`, `fileSuggestion`, `otelHeadersHelper`, `awsAuthRefresh`, `awsCredentialExport`, `gcpAuthRefresh`, `enableAllProjectMcpServers`, `enabledMcpjsonServers`, `disabledMcpjsonServers`, and `mcpServers`, and so does a key a later version of the agent CLI adds. A file that holds what the base's does written another way holds nothing. A lane with no base, such as an orchestrator's, has nothing to compare.

A hook in the frontmatter of a skill, a subagent, or a command runs as a settings hook does: skills and subagents take hooks "in the same configuration format as settings-based hooks" ([hooks](https://code.claude.com/docs/en/hooks#hooks-in-skills-and-agents)), and a command file supports the same frontmatter as a skill ([skills](https://code.claude.com/docs/en/skills#frontmatter-reference)). So the same check reads each skill's `SKILL.md` under `.claude/skills/`, and each Markdown file under `.claude/agents/` and `.claude/commands/`, at any depth and through links, as the CLI reads them, and compares the `hooks` its frontmatter declares with the same file at the same commit. A hook the lane added or changed there holds the lane as a listed settings key does, and so does a frontmatter that does not parse, since nothing can say it declares no hook. The check compares `allowed-tools` the same way, which a skill and a command take: the "Tools Claude can use without asking permission during the turn that invokes this skill" ([skills](https://code.claude.com/docs/en/skills#frontmatter-reference)) widen what the lane may do as a permission rule does, so tools the lane added or changed hold it, named `allowed-tools`, and tools it removed hold nothing. A subagent's `permissionMode` is compared too: it sets "the permission mode a subagent runs in", and in a session in `default` mode the subagent runs in the mode it sets ([subagents](https://code.claude.com/docs/en/sub-agents#permission-modes)), so a mode the lane added or changed, such as `acceptEdits`, holds it, named `permissionMode`. So do the shell commands a body runs before Claude reads it, inline as `` !`command` `` at the start of a line or after whitespace, or in a fenced block opened with ```` ```! ````: the page names the session's permission rules as their check and no `PreToolUse` hook ([skills](https://code.claude.com/docs/en/skills#inject-dynamic-context)), so a body whose commands differ from the base's holds the lane, named `!commands`. A piece with no hooks, a change to a piece's text alone, the same hooks written another way, and a hook the lane removed hold nothing. The check also reads the skills of each `.claude/skills/` directory below the worktree's root, which "load the first time Claude reads or edits a file in that subdirectory and stay available for the rest of the session" ([skills](https://code.claude.com/docs/en/skills)). The skills page names no directory discovery leaves out ([skills](https://code.claude.com/docs/en/skills#load-skills-in-monorepos-and-subdirectories)), so finding them reads the whole worktree but `.git`. Every path git sees, its tracked files and the untracked ones it does not ignore, is read in full from git's own listing, run with no hook, no file system monitor, no optional lock, and no lazy fetch. The listing runs through the git directory the member's clone records for the worktree, in its own `.git/worktrees`, with the worktree named as its work tree, and never through the worktree's `.git` file, which a lane can point at a git directory of its own whose `core.worktree` makes every listing succeed and list nothing. Where no single registration names the worktree, or git run in it does not name the worktree as its top level, the whole worktree is walked by names alone as the ignored directories are. The directories git ignores, such as `node_modules`, and those a listed link or submodule leads to, are walked by their names alone for a `.claude` that holds a `skills` directory, reading no file, for at most about 3 seconds. A large ignored tree with no skills holds nothing, and a skills directory found in one is compared as any other and named. A walk that runs out of time holds the lane, and the item says that the size of the tree holds the lane, and no change it made. The incomplete read binds only its reason to the hold's digest, never how far the walk got, so it adds the same part to the digest at every start and a member's choice for it still matches at the next. A reload's check reads the nested directories the generation's start found, so a nested skills directory a lane creates during a session is held at its next generation's start. A directory under a skills directory that holds a `.claude-plugin` directory loads as a plugin, with its hooks and MCP servers: a plugin is `<name>@skills-dir` when you "saved a plugin directory that has a `.claude-plugin/plugin.json` under `~/.claude/skills/` or the project's `.claude/skills/`" ([plugin loading](https://code.claude.com/docs/en/plugins/loading#find-where-a-plugin-came-from)). So the check compares every file under such a directory with the same path at the lane's base, and a plugin the base holds none of, or one with a file the lane added or changed, holds the lane, named `plugins`. Running with the repository's settings removes the `.claude-plugin` directory of a plugin the base holds none of, so it no longer loads, and puts back the files of one the base holds.

A hook the repository holds can also run a file the lane can edit, such as a script it names. A command hook runs "in the current directory", the session's working directory, which for a lane is its worktree, and `${CLAUDE_PROJECT_DIR}` is "the project root where the session started" ([hooks](https://code.claude.com/docs/en/hooks)). So the same check reads each hook the session would run, from its settings files and from its pieces' frontmatter, and takes each word of its command, split as a shell splits it, and of its `args` that names a regular file inside the worktree: a path such as `./x` or `scripts/x`, one under `$CLAUDE_PROJECT_DIR`, the value of a word such as `--file=x`, and an interpreter's argument, such as `bash scripts/x` or `python x.py`. The same words are read of the command of each settings file's `statusLine` and `fileSuggestion`, which run a command as a hook does ([settings reference](https://code.claude.com/docs/en/settings-reference)): a pane runs the repository's status line after ropeshift's own. A file that differs from the same path at the commit the lane's work began from, or that the commit does not hold, holds the lane as a changed hook does, and the item names the file, the key, and the hook or the setting that runs it. The commands read are the worktree's and the base's both: a restore of the repository's settings puts the base's hooks back, and a pane runs the base's status line whatever the worktree says, so a lane that edits the script a base hook runs and sets the worktree's hook to something else is held for the script all the same. A start that a restore leaves held anyway is refused. A file the lane removed holds nothing. The check reads only the words of the command, which is its known limit: a file a hook reaches indirectly, such as one a script sources, a Makefile target, a module an interpreter imports, a glob, or a path held in another variable, holds nothing, so a lane that changes only that file is not held.

A held generation parks before its session starts, with no process and no model call, and the lane reads Waiting on a member: this lane changed its own hooks/permissions. Needs you holds one item for the lane, in the security category, so only a member answers it, never an orchestrator or a delegate. It names the lane, the keys that changed, and a summary of each entry that changed, as plain text with credentials taken out and no environment value shown, held to 32 lines. It offers three choices:

- **Run with the repository's settings (base).** The recommended choice. The next generation's settings files, and each skill, subagent, or command whose hooks the lane added or changed, are put back as the commit its work began from holds them before its session starts, or removed where it holds none, and the generation is told so first; `project` stays among the setting sources, so the repository's own instructions, skills, and subagents still load. Nothing is written through a link, and a worktree whose `.claude`, or a directory on the way to a held piece, is a link fails to start.
- **Run with this lane's settings.** Recorded as the member's decision, a `lane.settings_decided` event on the lane, for that change alone: a lane that changes its settings again is held again.
- **Stop.** The work is blocked with the reason `settings_changed`, the parked lane ends, and its wake is retired, so the work waits for a member to resolve or replan it.

A hold that comes from a file a hook, a status line, or a file suggestion command of the repository runs offers no restore, because putting the file back would revert the lane's work: the item names those files, offers Run with this lane's settings and Stop, and recommends Stop, so the member either trusts the lane's version or sends it back, and a choice of the repository's settings is refused with `settings_not_restorable`. A hold from a settings file or a piece's frontmatter alone offers all three. Each choice binds to the change the member read, by its digest, and only a member makes it, through `POST /v1/work-orders/{id}/lane-settings` or `ropeshift lane settings`. A plain resume of a held lane is refused, whoever asks.

The CLI also reloads a settings file it watches when it changes during a session, hooks and permissions included ([settings](https://code.claude.com/docs/en/settings#when-edits-take-effect)), so the same check runs before each reload. Every session runs ropeshift's `ConfigChange` hook for the `project_settings`, `local_settings`, and `skills` sources, which the CLI runs before it applies a change, and whose block keeps "the new settings" from "the running session" ([hooks](https://code.claude.com/docs/en/hooks#configchange)). The hook asks the worker, which compares the worktree with the repository's at the commit the lane's work began from as a generation's start does. A reload applies when no key that runs code or widens access differs, or when what differs is the change the session started with, which a member chose. Any other reload is blocked, so the session never runs the new hook, permission, plugin, or server, and the lane is held as a generation's start holds it: its next tool calls are denied, it is asked once to hand off, and it parks with the same Needs you item, unless a member already chose for that change. The hook blocks too when it cannot reach the worker, is refused, or hears nothing within its bound, and the CLI blocks the reload when the hook fails or times out, through `onFailure`. A reload that changes nothing that runs code or widens access, but whose answer reaches the hook after its bound, is blocked all the same: the session keeps the settings it has until its next generation, whose start reads the files as they are and finds nothing to hold, and the late answer holds nothing. Hook entries from each settings layer are added together, so a lane's own settings cannot remove the hook, and the generated settings set `disableAllHooks` to `false`, which `--settings` holds over the project's and local settings ([hooks](https://code.claude.com/docs/en/hooks#disable-or-remove-hooks)). A blocked reload shows the person and the model nothing.

When the CLI reads the changed file during that check and apply is not documented, which is a known limit. The vendor says a hook runs "when a configuration file changes during a session", and that when it blocks, "the new settings are not applied to the running session" ([hooks](https://code.claude.com/docs/en/hooks#configchange-decision-control)), and names neither whether the CLI reads the file before it runs the hook or again after the hook allows it. The worker compares the file as the worktree holds it when the hook asks. So if the lane writes the file again between that read and the moment the CLI applies the change, and the CLI reads it after the hook, the session could apply what the worker never compared; the next generation's start compares the worktree again and holds it.

A hook a lane adds during a session to the frontmatter of a subagent or a command is held only at its next generation's start, which is a known limit. `ConfigChange` has no source for those files: its sources are the user, project, local, and policy settings files, and `skills`, for "a skill file in `.claude/skills/`" ([hooks](https://code.claude.com/docs/en/hooks#configchange)), so no hook asks the worker before the CLI takes the change. The CLI does take it within the session for a subagent: it "watches `~/.claude/agents/` and `.claude/agents/`", and when a subagent file changes, "the next delegation uses the updated definition, with no restart needed" ([subagents](https://code.claude.com/docs/en/sub-agents)). So a hook a lane writes into a subagent can run in the session that wrote it, the next time that subagent runs, and the lane is held for it when its next generation starts.

`CLAUDE_CODE_DISABLE_CLAUDE_MDS=1` is documented, and a lane does not set it: it drops every CLAUDE.md, the repository's own among them ([environment variables](https://code.claude.com/docs/en/env-vars)), and leaving out the `user` source already leaves out the member's. `--safe-mode` and `--bare` are not used either. The first turns off hooks and MCP servers, and ropeshift's own hooks and server hold a lane's rules and tools; the second does not use a subscription sign-in, and runs no hook passed with `--settings` ([CLI reference](https://code.claude.com/docs/en/cli-reference), [headless](https://code.claude.com/docs/en/headless#start-faster-with-bare-mode)).

## Recovery

An orchestrator recovers stuck work with no member, within a versioned `[recovery_policy]` that only a member publishes. The built-in version is this one:

```toml
[recovery_policy]
version = 1
restart_stalled = true
max_breaker_resets_per_day = 2
retry_failed = true
replan_blocked = true
max_attempts = 3
```

`max_attempts` is how many attempts a work order gets when it names no bound of its own. A work order's own bound wins, and no work order file sets one yet, so for now every work order has the policy's. A member's retry of work with no attempts left gives that work a bound of its own, one past the attempts it used.

It has four tools for it, each with the project, the work order, and a reason that must not be empty:

| Tool | Does | Within the policy when |
|------|------|------------------------|
| `lane_restart` | Ends a stalled lane's session and starts its next generation, which counts toward the lane's day | `restart_stalled` is true, and the lane runs on this orchestrator's machine |
| `lane_reset` | Resets a tripped breaker, so the lane starts again | The lane runs on this orchestrator's machine, it does not read `day_capped`, and orchestrators reset this work order's breaker fewer than `max_breaker_resets_per_day` times in the last day |
| `work_retry` | Returns failed work to `ready`, and the next lane reads why the last one failed and the reason | `retry_failed` is true, and the work has used fewer attempts than its own bound, or the policy's `max_attempts` when it names none |
| `work_replan` | Sends blocked work to `planning` with the reason and its lane's outcome, where its contract passes review again | `replan_blocked` is true |

`lane_restart`, `lane_reset`, and `work_retry` are refused for a work order at its hard spend limit, whatever the policy says: the check is `spend_limit`, the refusal names the work order, its limit, and what it is charged, and it raises no request, because a member's approval would be the spending the limit stopped. A member raises the limit with `ropeshift spend raise`, which an orchestrator cannot, and the act runs once the limit is above what the work order is charged. `work_replan` starts no spending and is never refused for it. A member's own `work retry`, `lane reset`, and `lane respawn` are held to the same limit, and so is an orchestrator's stop of a lane. A delegate holds the action that resumes a lane, so its `lane resume` of a lane that waits on a hard limit is refused: the limit is what the stop waits on, and only a member raises it or resumes the work. Blocking the work with `ropeshift spend block` and sending it to replanning with `ropeshift spend replan` are held to the same action as a raise, and a delegate's call of either is a confirmation card that no delegate policy exempts.

A project's daily or weekly limit is raised with the same action, a member's: `ropeshift spend raise --window day` and `--window week` lift the limit for the day or week they are made in, an orchestrator has no tool for it, and a delegate's call is a confirmation card that shows the limit before and after and that no delegate policy exempts. While the project is past a limit no work order of it is claimed, so a recovery act that would start a lane waits for the window to end or the limit to be raised.

A call whose work order or lane is no longer stalled, tripped, failed, or blocked answers with a conflict and records nothing: another actor already moved it. A call outside the policy changes nothing. It raises an approval request of kind `recovery`, bound to the act, its arguments, the reason, and a digest of the work order and lane as they stood, and the call's answer names it. The request waits in Needs you with the reason and the limit it went past, and the same call again finds the same request. Only a member decides one: approving it runs the act as the member's decision, and a retry of work with no attempts left gets one more attempt. The request is void once its work order or lane moves.

Every call that acts or is refused is a `recovery` event naming the act, the work order and its lane, the orchestrator and the generation of its session, the reason, the policy version in force, and the result. A failed lane leaves its work `failed` until someone retries it, so a crash that repeats does not spend every attempt unseen. The worker wakes its orchestrator for failed work, blocked work, and a lane its window tripped. Failed and blocked work wake it at every autonomy level, because a retry or a replan claims nothing and starts no lane; `lane_restart` and `lane_reset` run a lane's next generation, so they are held to `attended` or `unattended`. A wake for failed or blocked work quotes what its last lane reported when that lane failed or blocked it, which the orchestrator weighs and can give as its reason. A lane wrote that text, so the wake states it as plain text with each credential's shape redacted, cut at 600 characters, and the orchestrator's role reads it as a claim that grants nothing. A wake for failed work with no attempts left says so, because a retry of it reaches a member. The policy bounds orchestrators and not members: `ropeshift lane respawn`, `ropeshift lane reset`, `ropeshift work retry`, and `ropeshift work replan` do the same as a member. A takeover is never a recovery act: the control plane's takeover policy or a member reassigns lapsed work.

## The limit of same-user isolation

In solo mode, lanes run as the same operating system user as the person. The operating system does not separate them, so everything above raises the cost of self-approval and makes it visible. It does not make it impossible.

A lane with a shell can, as that user:

- Read another lane's token or a member's session from a process's environment, where the platform shows it.
- Read the worker's credential, and act as that worker's orchestrator for whatever a member delegated.
- Connect to any socket the user can reach, which includes the private terminal server, so a lane in a pane can press the key that answers its own prompt.
- Read and write the ledger and journal files directly. A database check stops a statement that breaks it, and it does not stop one that names a member as the decider. A window or an acknowledgement written that way passes for a member's. The event log would then disagree with the row, which a replay shows. The journal holds each token's digest, which is what a spool line's seal is keyed from.
- Read the stored passphrase hash, and guess at it offline.
- Change the generated settings and hook commands, past the guardrails that deny that write. A hook is a guardrail and not a sandbox.
- Run what it wrote through a repository's own hooks. An edit in the worktree and a commit both run with no prompt, and a commit runs those hooks, so where they run a file in the worktree, or `core.hooksPath` names a directory in it, a lane runs its own code at its next commit.

Strong separation needs a boundary an agent cannot cross: another operating system user, a container, a virtual machine, or a worker on another machine. Run a lane on untrusted work only behind one of these.
