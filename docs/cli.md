# Command line

`ropeshift` is a client of the versioned API, so it reaches the ledger the same way every other surface does. It finds the control plane's socket from the installation's paths, or from `--socket`.

A command that changes something needs a member's session, and a read on the local socket does not. With no session, the command asks for the passphrase on the terminal, for that one command. `eval "$(ropeshift login)"` holds a short-lived session in one shell instead. No file holds it, and no lane inherits it. The passphrase comes only from the controlling terminal, never from stdin, a flag, or a variable, so a process with no terminal cannot sign in.

Every command takes `--json`. With it, a result is one JSON document on stdout, and a failure is `{"error": {...}}` on stderr with the same exit code.

## Help

`ropeshift help`, `ropeshift --help`, and `ropeshift -h` list every command by group, each with one line, on stdout, and exit 0. `ropeshift help <command>` and `ropeshift <command> --help` print one command's usage, what it does, and its flags, and exit 0. A group's first word lists the commands under it, so `ropeshift help work` lists every `work` command.

`ropeshift` with no command prints the same list on stderr and exits 2: a missing command is a usage error, as an unknown one is. An unknown command or flag exits 2 and names `ropeshift help`. `ropeshift --version` is `ropeshift version`, and `ropeshift --version --json` prints its JSON.

`ropeshiftd` answers the same forms for its own commands: `solo`, `help`, and `version`.

## Projects

An installation holds one or more projects, and each project's records live in a ledger of their own. A command on a project's records acts on one project, which it takes from the first of these that names one:

1. `--project <name>`.
2. `ROPESHIFT_PROJECT`.
3. The project that holds the repository the command runs in: its remote, with no credential and no `.git` suffix, or its first commit when it has no remote.
4. The only active project.

With none of these, the command exits 2 and lists the projects. A name the installation does not hold exits 2 with the same list.

Every step of a project's lifecycle needs a member's session and records an event in the installation's log, with who took it.

A repository belongs to one project. Its identity is its remote, or its first commit when it has none, so every clone of one repository is the same repository. Registering a repository another project holds is refused with exit 4, and the message names that project.

Each repository has a name, unique in its project. A repository gets the name of its clone's directory, or the last part of its remote's path when another repository of the project holds that name, and a number after it when both are taken. Every repository command takes the name as well as the identity. A contract's `repo` names the repository a work order changes by that name, and `"."` or no `repo` names the repository that holds the contract file. A name the project does not hold is an intake problem that `source list` reports, and the work order fails the definition of ready, with the check `repository`, until a repository of the project takes that name.

A project plans in one repository, its planning repository. A project of one repository plans in it with nothing to set. A project of several names one with `repository set <name> --planning`, and naming another moves it. Once a project names one, intake reads goals, plans, documents, milestones, and contracts only from it, and each such file in another repository of the project is a problem that `source list` reports, so a plan in the wrong repository is seen and never read. A project of several repositories that names none reads plan files from every one of them.

The commands on the installation's own records take no project: `project`, `worker`, `orchestrator`, `login`, `sign-out`, `passphrase`, `init`, `service`, `health`, `telemetry`, which reads the worker's own store, `needs`, which reads every active project, and `backup --installation`.

One worker per machine serves every active project, and one orchestrator per machine serves every active project too. The daemon runs its ticks, intake, and notices in each active project, in that project's own database, and none in an archived project.

## Commands

| Command | Does |
|---------|------|
| `ropeshift needs` | Lists what waits on a member in every active project, the longest wait first, each item with its project, its kind, its ID, and how long it has waited. `--json` prints the combined Needs you |
| `ropeshift top [--once] [--width N]` | Watches the fleet: what needs a person first, in every active project, each item with its project and in the order the combined Needs you holds, then each lane of the project it resolved in that order with its state, reachability, and whether its value is `observed` or `last_reported`, then the workers. A parked lane says what it waits for, such as `waits for question q-1 or a person`. It follows the ledger's events and reads again at least every 5 seconds, and it changes nothing: it names the command for what the cursor stands on, with `--project` for an item of another project. Text from agents and repositories prints with control characters replaced. With no terminal, or with `--once`, it prints one frame, and `--json` prints one document. A printed frame is as wide as the terminal on stdout, and 120 columns when stdout is not a terminal, such as a pipe or a file. `--width N` sets its width in columns, and clips each line to it |
| `ropeshift health` | Says the control plane answered and read its ledger, and the revision the first project stands at, or 0 once the installation removed that project. It exits 9 when nothing answers |
| `ropeshift project list` | Lists the installation's projects, oldest first, each with its state, its display name, how many repositories it holds, and how many things wait on a member in it. `--json` lists the identity of each repository |
| `ropeshift project show <name>` | Shows one project: its ID, which every record of its ledger carries, its display name, its state, its database, and the record of each repository it holds |
| `ropeshift project create <name> [--display-name T]` | Creates a project with a ledger of its own, at the current schema, and registers it. The name is a lowercase, hyphenated slug no other project holds, used in addresses and `--project`. The ID is new, so the project's backup imports into any installation |
| `ropeshift project rename <name> <new-name>` | Changes a project's name. Its ID, its database, and every record keep their identity, and the old name names nothing |
| `ropeshift project archive <name>` | Makes a project read-only in every surface: it takes no claims and no change, and the daemon runs no intake, tick, or notice for it. It reads and backs up as before. It is refused, naming the lane, while any lane of the project has not ended, so drain it first with `fleet drain`. Archiving an archived project changes nothing |
| `ropeshift project restore <name>` | Returns an archived project to active. A project that is not archived exits 4 |
| `ropeshift project remove <name> --confirm <name> (--backup F \| --no-backup)` | Deletes an archived project's database and drops it from the registry and the repository index, after writing its backup to F when `--backup` names a file. It exits 2 unless `--confirm` repeats the name and exactly one of `--backup` and `--no-backup` is given, and 4 for a project that is not archived. The installation's first project is removed like any other |
| `ropeshift project import <file> [--name N]` | Registers a project from its backup, keeping its ID, under `--name` or the name its backup holds. It exits 4 when the installation holds that ID or name, or when another project holds one of its repositories, which the message names. A relative path is read from where the command runs |
| `ropeshift version [--json]` | Prints the version, the commit, the build date, the Go version, and the platform. It needs no daemon, and `ropeshiftd version` prints the same under the daemon's name. `--version` is the same command. See [versioning](versioning.md#what-a-binary-reports) |
| `ropeshift help [<command>]` | Lists every command by group, or prints one command's usage, what it does, and its flags. See [help](#help) |
| `ropeshift work create --title T [--criterion C]...` | Records a work order and the contract it pins, in `contract_review`. With `--kind plan --repository R`, its lane writes repository files on its branch, and intake reads them at the commit a member accepts. The files are goals, plans, requirements, specs, architecture documents, experience designs, milestones, and contracts, and intake keeps a numbered version of each document for every committed change. A contract pins each document it cites to the version at its commit, and a criterion that serves no requirement of its plan keeps the work from `ready`. A contract names the milestone of its plan it belongs to, which every contract of a plan with milestones must do, and the shared contracts of its plan it uses, and a milestone names the milestones it depends on. Intake makes every work order of a milestone wait for every work order of the milestones it depends on, and every work order of a contract wait for the work orders of each shared contract it uses. A reference to a milestone or shared contract the plan does not hold is a problem, and intake records nothing from that file. A plan whose milestones, shared contracts, or work orders depend on each other in a loop is refused whole, and the problem names the loop. Files can also say what already exists: a requirement with `status = "met"` and `evidence` the code already meets, and needs no criterion; a milestone or contract with `existing = true` is delivered already, a contract so marked has no work orders, and nothing that depends on either waits for it; a contract with work orders in an existing milestone is a problem. A work order's `continues` names an in-flight branch it finishes, and a plan's `[[left_out]]` tables record each branch or issue it does not carry, with the reason. `source list` names R, and reports a file intake could not read. `--agent` names the roster agent the work's lane runs as, and a contract file's work order names one in `agent`, which a planning session proposes and plan approval covers. With none, the roster's default mapping chooses by kind and size: `plan` runs as `reasoning`, `contract_review` as `analysis`, a review as `review`, and a change by its size as `light-implementation`, `implementation`, or `heavy-implementation`, with an absent size counted as medium. Work sent back moves one implementation tier up, never into an agent whose approval is per use. Work whose agent is unknown or disabled fails the definition of ready, naming the agent |
| `ropeshift work list [--state S] [--worker W]` | Lists work orders. With `--worker`, it lists only ready work that worker's manifest can run |
| `ropeshift work show <id>` | Shows one work order, then a `pull request` line when it lands through one (its number, its state, `open`, `closed`, or `merged`, its head commit, and its address), then the reviews it has had as `review` lines (the review, its state, and the attempt it judged) and the verdicts that speak for its current attempt as `verdict` lines (the criterion, `pass`, `fail`, or `cannot_judge`, the reviewer's reasons on one line, and its citations). Each approval of a reviewed commit for merge is an `approved` line: the commit, who approved it, the merge authority level, and the commit it merged as once it landed. When the verdicts hold the work for a member, a `waiting` line says what for, and for work in `integrating` it says what the merge waits on. With `--json`, the reviews are in `judged_by`, the verdicts in `verdicts`, the reason in `why`, the pull request in `pull_request`, and the approvals in `integrations`, beside the work order's own fields. A `review` work order, which ropeshift makes when a lane completes a change that left a commit, names the work order it judges in `reviews` and the attempt in `reviews_fence`. `base` names the branch its contract file asked to start from, and `waiting` names why ready work is not claimed: `waiting_for_merge` for a dependency whose accepted work is not yet in the base branch, `dependencies_diverge` for dependencies whose accepted work is on separate lines, `base_unavailable` for a base branch that could not be fetched or does not exist, `continued_branch_missing` for a branch the work continues that neither the remote nor the checkout holds, and, for a review in a repository that reviews through pull requests, `pull_request_pending` until the worker has pushed the branch and its pull request is open with the commit under review as its head, and `forge_unavailable` while that worker's `gh` is missing or signed out. The reason clears by itself once it no longer holds, and a claim that meets it is refused with exit 4 and the same words |
| `ropeshift work review <id>` | Records a passed review, and the definition of ready decides the move to `ready`. Work whose contract version an approved plan version lists needs no review of its own, because approving the plan passed it |
| `ropeshift work acceptance <id>` | Shows what a work order's evidence leaves to do, with every artifact and check result linked to it, and the reviews and verdicts of its current attempt |
| `ropeshift work accept <id>` | Moves completed work to `done`. A failed check cannot be accepted, and a criterion no check maps to needs a member, because no agent stands behind a lane's own checks. Work whose review is still open can be accepted, and doing so cancels that review. With review target `branch` at `person_merges`, finished work waits for this command, with the review's verdict for each criterion beside it. Through a pull request, and in a repository at `person_approves` or `review_approves`, accepted work moves to `integrating` instead: at `person_merges` it waits there for your merge on GitHub, and otherwise ropeshift merges it; accepting work already in `integrating` approves the merge of its reviewed commit, as [onboarding](onboarding.md#merging-accepted-work) describes |
| `ropeshift work rework <id> --reason R` | Sends completed work back to `ready` for another attempt, and cancels a review that is still open. Its evidence stays on record and stops counting, and the reason reaches the next attempt's first prompt as why the work came back. A criterion a review failed sends work back without you, until the review has judged it `max_review_rounds` times |
| `ropeshift work claim <id> --worker W [--claim-id C]` | Claims a work order for a worker. A retry with the same claim ID returns the grant |
| `ropeshift work release <id> --claim-id C --fence N` | Gives back a claim whose lane has not started |
| `ropeshift work write <id> --claim-id C --fence N [--write-id W] [--lane L --generation G] --payload P` | Stores one event under a claim's fence. A retry with the same write ID stores one event, and a stale fence exits 5 with the current one in the message |
| `ropeshift work reassign <id> --reason R` | Ends a lapsed holder's ownership, which moves the fence |
| `ropeshift work cancel <id> --reason R` | Ends a work order for good, from any state that is not terminal, which only a member can do. Any claim ends and the fence moves, so a lane can write nothing more. A parked lane ends at once. A lane with a process stops through the guard when its worker hears, saves what it holds to a ref, and reads as last reported until then. Canceling work that is already canceled changes nothing, and finished or failed work exits 4 |
| `ropeshift work send-back <id> --reason R` | Returns a work order in review to `planning`, because its contract must change. It voids the review, and the contract's next version returns the work to review |
| `ropeshift work resolve <id> --reason R` | Returns blocked work to `ready` with its review standing, once whatever stopped the lane is fixed |
| `ropeshift work replan <id> --reason R` | Returns blocked work to `planning`, which voids its review, because its contract must change. Only a member can take work out of `blocked` |
| `ropeshift work retry <id> --reason R` | Returns failed work to `ready` for another attempt. A failed lane leaves its work `failed` whether or not attempts remain, and nothing retries it on its own. A work order has the attempts `[recovery_policy]` states in `max_attempts`, 3 by default, unless it names its own. Work with no attempts left gets one more, which only a member can give. The next attempt's first prompt says why the last lane failed and why the work was retried |
| `ropeshift adopt [<path>...] [--project P] [--planning NAME] [--worker ID] [--no-attach]` | Adopts the project in the repository it runs in, which must hold a commit, and attaches your terminal to the adopt session. It makes the calls a member makes by hand, each one recorded as yours. It uses the project that holds the repository, or else the one `--project` or `ROPESHIFT_PROJECT` names, or else a project named after the repository's directory, in lowercase with a hyphen for anything else, and creates that project when the installation has none by the name. It registers the repository and every clone at or one level below each path, as `repository add` does, prints what became of each, and goes on when a clone other than this repository is refused. A project of one repository plans in it; a project of several plans in the repository `--planning` names, or the one the project already plans in, or else asks on the terminal which one holds the plan, and with no terminal stops with exit 2 and the names to choose from. The worker is `--worker`, or the only worker registered, or the only one of several whose word is fresh, and otherwise the command lists them and stops. The repository is `--repository`, or else the project's planning repository, which a member names with `repository set --planning` and which a project of one repository has by default, or else the one the daemon reads. With no terminal, with `--no-attach`, or with `--json`, it starts the session and prints the lane, the `lane attach` command that joins it, and the session's page in the web UI, at the address the daemon says its web UI listens on, with the port it bound even when `--web` asked for port 0. ## The daemon

`ropeshiftd solo` runs the control plane and this machine's worker in one process. `ropeshift service install -- <flags>` passes the same flags to it under the service manager. `ropeshiftd help` lists the daemon's commands, and `ropeshiftd solo --help` prints these flags with their defaults.

| Flag | Default | Meaning |
|------|---------|---------|
| `--source <path>` | None | A repository to read work and documents from, into the installation's first project. Repeat it for each repository. A repository another project holds is refused: each read says which project holds it, and reads nothing from it. Intake also reads, in each project, every repository `repository add` registered there from this machine |
| `--ref <ref>` | The default branch | The ref intake reads in each source |
| `--dir <dir>` | The whole repository | The directory intake reads in each source |
| `--web <address>` | `127.0.0.1:7317`, or `ROPESHIFT_WEB` | The loopback address of the web UI, or `off` |
| `--telemetry <address>` | `127.0.0.1:7318`, or `ROPESHIFT_TELEMETRY` | The loopback address of the telemetry receiver, or `off`. See [telemetry](telemetry.md) |
| `--intake-tick <duration>` | `30s` | How often sources are read |
| `--notify-tick <duration>` | `30s` | How often members are told what waits. See [notifications](notifications.md) |
| `--forge-tick <duration>` | `1m` | How often the worker reads `gh`'s sign-in for each repository that reviews through pull requests, and each pull request it watches, and how long a failed push or pull request waits before its next attempt. See [onboarding](onboarding.md#review-through-pull-requests) |
| `--telemetry-tick <duration>` | `5s` | How often the ledger is read into spans and metrics |
| `--lease-tick`, `--batch-tick`, `--wake-tick` | `5s`, `5s`, `1s` | How often lapsed leases end, closed question batches reach members, and due wakes fire |
| `--lease-ttl`, `--heartbeat` | `60s`, `15s` | How long a lease lasts, and how often the worker beats |

An installation keeps its ledger, installation database, journal, and telemetry store in its state directory, and its sockets in its run directory. The ledger, `ledger.db`, holds the default project's records. The installation database, `installation.db`, holds the registry of projects, the member and the passphrase's hash, the member sessions, the workers with their autonomy and run windows, and the orchestrators. A daemon started on an installation with only a ledger moves those records into a new installation database and keeps the ledger file where it is:

| Directory | macOS | Linux | Moved by |
|-----------|-------|-------|----------|
| State | `~/Library/Application Support/ropeshift` | `$XDG_STATE_HOME/ropeshift`, or `~/.local/state/ropeshift` | `ROPESHIFT_STATE_DIR` |
| Run | `~/.ropeshift/run` | `$XDG_RUNTIME_DIR/ropeshift`, or `~/.ropeshift/run` | `ROPESHIFT_RUN_DIR` |

A second installation on one machine sets both variables and its own `--web` and `--telemetry` addresses.

## Exit codes

| Code | Meaning | What to do |
|------|---------|------------|
| 0 | The command did what it said | Nothing |
| 1 | The control plane could not answer, or the command failed for another reason | Retry, and read the message |
| 2 | The command line or the request is invalid | Fix the command |
| 3 | The record does not exist | Check the ID |
| 4 | The ledger's state refused this: a claim was lost, work was not lapsed, the move has no edge, or a removal would lose work no remote holds | Read the current state |
| 5 | The fence is stale: another holder owns this work | Stop, and read the current fence in the message |
| 6 | The lease lapsed and this holder can return | Return, then retry |
| 7 | The review is recorded, and the definition of ready names what still holds the work back | Resolve what it names. The work order moves on its own |
| 8 | This actor may not take this step, or the step needs a member's session and has none | Use an actor that may, or sign in on a terminal |
| 9 | Nothing answered on the socket | Start the daemon, or check `--socket` |
