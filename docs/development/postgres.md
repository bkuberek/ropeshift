# The Postgres adapter

`internal/adapters/postgres` keeps an installation on one Postgres database: the installation's own records in the `installation` schema, and each project in a schema of its own, named `project_<id>` with the ID in lowercase. It shares the statements of `internal/adapters/sqlstore` with the SQLite adapter, and `make check-postgres` runs the store contract suite and the adapter's own tests on a private server. The server's binaries come from `PATH` or from the directory `ROPESHIFT_TEST_PG_BIN` names. No solo binary imports the adapter, and `make check` holds that.

## Connections

The projects of an installation share one pool of connections, and the installation has a pool of its own. `Options.MaxConns` bounds each of them, and neither is ever smaller than 2. The two are separate because one pool deadlocked: a project's transaction holds a connection while it reads the installation's records through a second one, so enough writers on one pool each held a connection and none got the second.

A project's write holds one connection of its pool, and at most one of the installation's. The installation's side of a write begins at its first statement, read-only, and a write that registers a repository swaps it for a writing one at that point. The side commits, or ends if it only read, when the write's function returns and before the project's transaction commits.

## The migration lock

Every step that makes a schema, migrates one, or drops one runs under a session advisory lock on one fixed key (`postgres.MigrationLock`), so processes that start together apply each version once. A caller takes its turn in its own process first, and then polls `pg_try_advisory_lock` on a connection of the project pool, which it keeps for as long as it holds the lock. The work under the lock runs on other connections of the pool, so the pool is never smaller than 2.

A caller waits for the lock until its context ends or `Options.LockTimeout` passes, one minute unless the option says otherwise, and then fails with `postgres.ErrLockTimeout`. The timeout covers the whole wait: the caller's turn behind the other callers of its process as well as the time another process holds the lock, so the error does not always mean that another session holds it. It does not bound the work under the lock. The default of one minute also caps how long a server start waits behind another process's long migration; a deployment whose migrations take longer sets `LockTimeout` above the longest one, or to a negative value to wait for as long as the start's context lasts. A project whose Store the process already holds comes back from `Open` without touching the lock. A session that holds the lock and stops is a defect to find on the server: `pg_locks` lists it with `locktype = 'advisory'`.

## Creating, opening, and removing a project

The registry decides which projects exist. A project's schema is named `project_` and its ID in lowercase, so a generated ID, which is in capitals, gives a name `psql` reads without quotes. Two IDs that differ only in case name one schema, and `State.Create` refuses the second. A project an earlier build registered on a schema that kept the ID's capitals still opens and is removed with that schema, and `State.Create` refuses an ID that differs only in case from such a project's, although the two schemas differ.

`State.Create` runs under the migration lock from the first check to the registry's row: it refuses a name or a schema another project holds, makes the schema, migrates it, makes the workspace, and registers the project. The Store it opened is cached only after the lock is released. A step that fails without a crash drops the schema this `Create` made, unless the registry names the project, because the failed step may have committed. A registry step whose connection was lost in the middle of its commit may still commit after that check, and a repeat of `Create` with the project's ID then makes the schema again. A schema that an earlier `Create` or a person made is not one it drops.

A crash after the schema and before the registry's row leaves a schema no project names. A retry with the same ID registers it, and `postgres.Open` drops the rest under the lock, so one that a `Create` is making is never one it drops. It drops a schema only when no registered project names it and its name is `project_` and an ID the adapter generated, a ULID in lowercase or, as an earlier build wrote it, in capitals. A schema a person made under the prefix, such as `project_pa_backup`, stays. A schema that cannot be listed or dropped stays too, with a warning through `Options.Store.Warn`, and the next `Open` tries again: `Open` fails on the sweep only when it cannot read the registry.

`postgres.Open` also repairs the repository index. A project write enters and releases repository identities in the index in a transaction that commits just before the project's, so a crash between the two, or a commit of the project's that fails, leaves the index disagreeing with the records. It may hold an entry whose record never came or is still removed, or the identity of a remote move that did not happen while the record keeps its own, and it may lack the entry of a record that a removal released, including a removal of one record of a repository that another record of the project shares. Until it is repaired, another project can register the repository of a record that has no entry, and none can register the repository of an entry whose record does not hold it.

Under the lock, `Open` reads each project's repository records, compares them with the project's entries, and rebuilds the entries of a project where they disagree. Entries and records agree when each entry names a record that is not removed, at the identity that record holds, and the entries between them hold the identity of every such record; two records of one repository share one entry, whichever of them holds it. A rebuild takes the project's revision, the row every write of the project takes first and holds until it commits, and compares again, so a write that is committing is finished by then and its entries stay. It then replaces the project's entries, in one transaction, with one per identity that its records that are not removed hold, and leaves every other project's entries alone. A record whose identity another project holds in the index gets no entry, and `Open` warns about it. It also releases the entries of a project the registry does not hold. It does not rebuild the whole index from the records, as SQLite does at every start, because another process may be in the middle of a write. A project whose revision stays busy for more than five seconds, or whose schema cannot be read, is left with a warning for the next `Open`.

A caller that sees a write of a project fail can run the same rebuild for that project without opening the state again. The rebuild takes the migration lock, as `Open` does.

`State.Open` returns the Store the process already keeps for a project, and otherwise reads the registry under the lock and refuses a project it does not hold with `ports.ErrNotFound`, so it never makes the schema of a project a removal has forgotten. `State.Remove` takes the lock first and runs both of its steps under it: it deletes the registry's row and then drops the schema, so an `Open` or a `Create` in another process cannot register the project or make the schema again while it drops. The drop waits for the locks of the schema's tables for 30 seconds at most, and then fails with the schema as it was, because it runs under the migration lock and a session with a transaction open on one of the project's tables would otherwise hold up every other caller; the registry has forgotten the project by then, and a repeat of `Remove` finishes the drop. The drops of the sweep and of a failed `Create` have the same bound. It reads the registry before it deletes anything, and it refuses a record whose schema is not the one the registry keeps the project on, so a stale or forged record never drops another project's schema. A record of a project the registry has already forgotten, which a `Remove` that crashed after its first step leaves, finishes the drop unless a registered project holds that schema.

## Between the adapter and the database

The migration lock is a session advisory lock, which belongs to one server connection from the call that takes it to the call that releases it. A connection pooler in transaction pooling mode hands each transaction to any server connection, so the lock could be taken on one and released on another, or stay on a connection that serves someone else. PgBouncer lists session-level advisory locks as supported in session pooling and never in transaction pooling ([PgBouncer features](https://www.pgbouncer.org/features.html)). Point the adapter at the database itself, or at a pooler in session pooling mode.

pgx prepares each statement on first use and caches the prepared statement on its connection, by the statement's text ([pgx `ConnConfig`](https://pkg.go.dev/github.com/jackc/pgx/v5#ConnConfig)). A connection of the project pool serves every project, and a transaction picks its project by setting `search_path`, so one statement text runs against each project's schema in turn. PostgreSQL parses a prepared statement again when `search_path` changes ([PREPARE](https://www.postgresql.org/docs/current/sql-prepare.html)), so the statement reads the right tables. What pgx keeps is the description of the statement's result, and a statement whose result has other columns in another schema fails with `cached plan must not change result type` ([plancache.c](https://github.com/postgres/postgres/blob/master/src/backend/utils/cache/plancache.c)).

The cache therefore assumes that every project schema the process uses is at one version. `State.Open` brings a project's schema to the process's version before it returns the Store, so the assumption holds inside one process. It does not hold across two builds that share a database while a migration changes the columns of a statement's result. Stop the old processes before the new build opens the database.

## Idle transactions

Every connection sets `idle_in_transaction_session_timeout`, 30 seconds unless `Options.IdleInTransaction` says otherwise, so a process stopped inside a transaction cannot stall every writer of its project. The two transactions of a write are idle in turn: the project's while the installation's side runs a statement, and the side's while the project runs one.

A project statement that runs longer than the timeout between two uses of the installation's side ends the side's session, and the write fails. The same holds the other way: a statement of the side that waits for a lock, such as the repository index's, can outlast the timeout of the project's session. Writes are short by design, because the project's revision lock is taken first (ADR-0010). A deployment that runs a long statement in a write sets `IdleInTransaction` above the longest one, or turns the timeout off with a negative value.
