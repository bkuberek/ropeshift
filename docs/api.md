# API

Every surface of ropeshift is a client of one versioned HTTP API: the command line, `ropeshift top`, the web UI, and the worker. On the local machine the API listens on the control plane's socket, which only its owner can reach, and the web UI reaches a closed list of its routes through the web listener.

## Routes

An installation holds one or more projects, and the API names the project in the path of every route on a project's records:

| Routes | Under | What they reach |
|--------|-------|-----------------|
| The installation's | `/v1/` | The registry of projects, members and their sessions, the passphrase, workers with their autonomy, run windows, and orchestrators, the worker's telemetry, the health of the control plane, the installation's backup, the project templates, the combined Needs you, and the protocol a worker speaks with its credential |
| A project's | `/v1/projects/{project}/` | Everything else: work orders, lanes, plans, requirements, documents, questions, decisions, policies, approvals, effects, notices, repositories, the fleet's mode and caps, the read models, the event stream, measures, and backups |

A route on a project's records with no project in its path does not exist and answers 404.

`{project}` is the project's name, as `ropeshift project list` prints it. A name the installation does not hold answers 404 with the code `no_project`, and a record of another project answers 404 with `not_found`, because a project's routes read only that project's ledger. A repository another project holds answers 409 with `repository_held`, and the message names that project. A change a repository's record refuses as it stands, such as a name another repository of the project holds, answers 409 with `repository_state`.

`GET /v1/projects` lists the projects, each with its state, the identity of each repository it holds, and how many things wait on a member in it, and `GET /v1/projects/{project}` shows one with its database and its repository records. A member's session takes a project through its lifecycle, and each step records an event in the installation's log:

| Route | Body | Step |
|-------|------|------|
| `POST /v1/projects` | `{"name": "...", "display_name": "..."}` | Create. The server trims space from either end of `display_name`, which then holds at most 100 characters, no control character, and no invisible format character such as a zero-width space or a text-direction override, except a zero width joiner or non-joiner between two visible characters, as in an emoji sequence or a Persian name |
| `POST /v1/projects/{project}/rename` | `{"name": "...", "display_name": "..."}` | Rename, and set the display name, which the server trims and refuses as it does on a create; with no `display_name` the project keeps the one it has, and with the name it has it changes only the display name |
| `POST /v1/projects/{project}/archive` | `{}` | Archive, once every lane ended |
| `POST /v1/projects/{project}/restore` | `{}` | Restore |
| `POST /v1/projects/{project}/remove` | `{"confirm": "...", "backup": "..."}` or `{"confirm": "...", "no_backup": true}` | Remove an archived project |
| `POST /v1/projects/import` | `{"path": "...", "name": "..."}` | Import a project's backup, keeping its ID |
| `POST /v1/projects/import/upload` | `{"backup": "<base64>", "name": "..."}` | Import a backup the request carries, as a browser uploads it, up to 128 MiB |

An archived project answers every change with 409 `project_archived`, a backup excepted, and a step its state refuses answers 409 `project_state`.

The `id` a client names for a work order, a contract review, a question, a decision, or a lane is 1 to 64 ASCII letters, digits, `-`, and `_`, as every ID ropeshift and its clients generate is, and any other answers 400 `invalid`, because an agent reads it wherever it reads the record. A decision's `id`, whether a client records the decision, answers a question with it, or overturns another decision with it, may not start with `pd-`, which only plan approval names decisions under, and one that does answers 400 `invalid`, for a member as for a delegate. New work's `requirements` are keys a requirements file names, such as `FR-LANE-1`: 1 to 64 ASCII letters, digits, `-`, `_`, and `.`. Its `repository_id` is plain as an `id` is. Any other answers 400 `invalid`, because an orchestrator's `work_candidates` states both with nothing around them. A question's `subject_kind`, when it names one, is `work_order`, `contract`, or `plan`, and its `subject_id`, when it names one, is plain.

A question's fields are bounded, because a member reads each one in a batch. Its text, each option, its recommendation, and the recommendation's rationale are each at most 2000 bytes, and it offers at most 20 options. A question that asks, and an escalation that replaces its options, recommendation, or rationale, both trim the whitespace around each option, the recommendation, and the rationale, and drop an option that is empty after trimming. A field over its bound, or more than 20 options, answers 400 `invalid`, and its message names the field and the bound. The question tools of the MCP server send these fields to the same routes, so they hold the same bounds.

The `decisions` view gives each decision's `decided_by_kind`, the kind of party that recorded it, such as `member` or `orchestrator`, as the event that recorded it names, so a decision whose orchestrator's worker the ledger no longer holds still reads as an orchestrator's, and `decided_by_name`, the name of the worker whose orchestrator recorded it, while the ledger holds that worker. A read of decisions, the list, one decision, and the `decisions` view, gives each decision's `scope_title`: the title of the record its scope names, read in the same read, which is a plan's, a contract's newest version's, or a work order's title, or a repository's name. A read of questions, the list, one question, the `questions` view, the question batches, each batch in `needs_you`, each question in a lane's stream, and the `open_questions` of each review in the `plans` view, gives each question's `scope`, the scope an answer to it takes from the record it is about, and its `scope_title` the same way, and its `reversibility`, `reversible` or `one_way`, which is what an answer to it will be. Its `overlaps` names, by ID, the decisions in force whose scope overlaps its scope, which an answer can replace. A question that still waits, whether open, held, or waiting for a person, names those in force at the read, and a read of many questions reads the decisions in force once for all of them. The ledger keeps those a question overlapped when it reached a person. `scope_title` is absent when the ledger holds no such record, for a scope written before `plan:`, `contract:`, `wo:`, and `repo:`, and when the record's title only repeats its ID. A read takes one store read for each kind of scope its records hold, however many records it lists, and it reads only the plans, contracts, and work orders those scopes name.

The `plans` view gives `ready_waits`: for each ready work order that no worker's orchestrator will claim, why not, which the control plane reads at the time of the read from what a claim reads, and which no event holds. `reason` is `fleet` for a fleet a member paused or set to drain, with `fleet` its mode; `spend_limit` for a project past its daily or weekly spend limit; `cap` for a cap a claim would pass, with `cap` naming it as a fleet's caps or the autonomy policy do: `wip_limit`, `lanes_per_repository`, `lanes_per_worker`, or `attended_max_respawns_per_day`, the bound on the generations a day of a lane a wake made ready; `run_window` for an attended worker with no run window open; `no_orchestrator` for a worker whose orchestrator no member wants running; `manual` for a manual worker; and `no_worker` for work whose needs or lane no worker meets. A reason that is one worker's carries `worker` and `worker_name`, the worker nearest to claiming the work, in that order of reasons. Work a wake made ready is claimed by the worker that holds its lane, with nobody there and no orchestrator, so the level, the run window, and the orchestrator never hold it, and the bound on its lane's generations a day does. Work that resumes a lane the ledger does not hold reads `no_worker`. A work order a worker will claim has no entry, and the field is absent when no ready work waits. A member's own claim passes the level and the run window, and is held to the caps.

A question and each question of a batch carry the shape its asker gave it, when it gave one: `title`, the question in a few words on one line, of at most 120 bytes; `tradeoffs`, what choosing each option gives up, as an object keyed by the option; and `unblocks`, what the answer lets go on. A tradeoff must name one of the question's options, and a batch item lists a tradeoff only for an option the question still offers. The same reads give each question its whole ladder. `holder` is who holds it while the hold lasts, with `id` and `until`, and for an orchestrator its `orchestrator` and the `machine` it runs on; it is absent when nobody holds the question. `attached` is every lane that asked it or waits on it, `batch` the batch that gathered it, `closed_by` the decision or assumption that answered it, and `merged_into` the question that took its place. `machines` names the machine of each orchestrator its `ladder_trace`, `holder`, or `closed_by` names, by its worker's ID. The `questions` view holds the open questions at every rung, and its filters read the rest: `status` is a question's status (`open`, `triage`, `needs_human`, `answered`, or `dismissed`), `merged`, or `all`, and a question a merge closed reads as `merged` and not as `dismissed`. `lane` keeps the questions a lane asked or is attached to, and `work_order` those about a work order or asked by one of its lanes. Each filter narrows the others.

`POST /v1/projects/{project}/work-orders` with `"kind": "plan"` and `"adopt": true` records planning work that adopts an existing project: its lane is a planning lane told to onboard what the project holds, and the worker writes the inventory of the project's repositories into its context folder before it starts. Only planning work adopts, and any other kind answers 400 `invalid`. A project that already has an approved plan answers 409 `already_planned`, because it plans its next work with a planning session. Adopting work may carry `"restructure": {"shape", "digest", "design_path", "design_root", "leave_out", "root", "paths", "depth", "planning", "design", "parts"}`, the restructuring a member chose from the plan of the layout (`POST /v1/projects/{project}/adoption/plan`, below), which the work order keeps. `shape` is `planned`, `consolidate`, or `workspace_files`, `digest` is the plan's, and the rest belong to `consolidate`: the design repository's clone and first-parent root, and the code trees to leave out. `root`, `paths`, `depth`, `planning`, and `design` are the request the plan was read with: the clone adopt ran in as a clean absolute path, the absolute paths named beside it, how many levels below a folder were searched (at most 4), and the clone folder names `--planning` and `--design` named. `parts` maps the name of each part of the plan (`layout`, `shape`, `planning`, `design`, `repositories`, `files`, `takes`, `collisions`, `code_trees`, `moves`) to its SHA-256 digest, so a worker that reads another layout names the parts that differ. All of them are optional, and a restructuring kept without `root` and `parts` is kept as it was sent, but a worker cannot read the layout again from it. A restructuring on work that does not adopt, or with the shape `single`, or with no digest, or with a root or path that is not absolute, a depth above 4, or a part nothing digests, answers 400 `invalid`, and only a member may send one: a delegate's call that carries it answers 403 `member_only`.

`POST /v1/projects/{project}/work-orders/{id}/lanes` takes `{"lane_id": "...", "overrides": "..."}` and asks the worker holding the work order's claim to run that lane. `overrides` is the lane's own profile layer, as TOML, over the built-in, user, and repository layers. Overrides that are not TOML, that set `driver`, `hooks`, `agent.credentials`, `agent.instructions_file`, `worktree.root`, or `worktree.branch_prefix`, that set `review.max_review_rounds` to anything but `1` or `resources.ports_per_lane` to anything but `0`, or that hold two keys of one table that differ only in case, answer 400 `invalid` whoever calls, and the ledger keeps nothing of the request. A key counts in every spelling the profile reads as that key, because the profile matches keys under Unicode case folding: `[Hooks]`, `[HOOKS]`, and `ROOT` in `[worktree]` are refused as well. The route holds neither the user's layer nor the repository's, so it can judge only the floor of `review.max_review_rounds` and `resources.ports_per_lane`, one round and no ports, which no layer below can be under; the worker compares any other value with those layers and refuses a layer that raises either bound. `agent.gates` is not refused: the gates of every layer join, so overrides that set it, even to an empty list, can only add a gate. The worker refuses a layer that changes any of the other keys when it reads it, and layers that spell one key two ways. It also refuses a layer that sets a higher `max_generations_per_day` or `max_restarts`, or a shorter `restart_window`, than the user's and the repository's layers give, and one that raises the permission mode past the user's, changes `push_on_stop`, `[agent.classes]`, `[projects]`, what the machine admits, how the worker measures, or the worker's telemetry store or export, or turns content capture on, and the lane then fails to start; a lower cap or a longer window is allowed. A delegate's start that sends `overrides`, the assistant's or an outside delegate's, records on the claim the delegate and the version of the delegate policy in force, and a claim that brings the lane back keeps it. While that version sets `raise_model_and_effort = false`, the worker refuses overrides that raise the model's capability class or the effort past what the lane would run without them, which is what the roster agent the lane runs as runs, and the lane fails to start: its work fails with the reason `delegate_policy`, and the `detail` of the event that ends the lane, and of the work in the `completed` view, names the version and what the overrides raised; a member's overrides are never held to it ([authorization](authorization.md#delegates)). [Onboarding](onboarding.md#a-lanes-own-profile-layer) lists each rule.

`POST /v1/projects/{project}/repositories` registers repositories in the project from git clones on the machine of the daemon's worker, and needs a member's session. It takes `{"paths": [...], "depth": N, "dry_run": true}`, where each path is absolute. A path that is the top of a clone is that clone, and any other directory holds the clones among its children, down to `depth` levels, one by default. The answer lists each clone and each path with its `outcome`: `registered`, `known` for a repository the project holds already, or `refused` with a `reason`, such as another project holding the repository or a path that holds no clone. A refusal registers nothing for that clone and stops none of the others, and a dry run records nothing. A clone's `path` is where the worker read it with every symbolic link followed, which is how the project matches and keeps it; when the member reached it through a link, `entered` carries the path as they named it, or as found below one they named, and a client shows that in place of `path`. In place of `paths`, `"manifest"` takes the text of a repository manifest, which only a member's session may send, as a delegate's call answers 403 `member_only`, and each repository it lists is registered from the clone at its path beside the planning repository's clone, under the manifest's name, or refused with why; a text that is no manifest answers 400. A member's approval of a plan version, through `POST /v1/projects/{project}/approvals/{id}/decide`, registers what that version's manifest adds in the same way, leaving out a repository a member removed, by its name or by its remote, and its answer carries each outcome in `repositories` (an approval registers once, so deciding an approved version again answers with what the first decision recorded and registers nothing more), and in `repositories_problem` why registration could not run, when it could not; the approval stands either way. An entry with `create` that a work order of the version names in `repo` is created by that approval, on the machine of the daemon's worker, and then registered: the approval runs again the checks that come before a write, records `approval.repository_creation_started`, with the entry's `path` and `leads`, where that path leads on that machine with every link followed, creates the repository, and records `approval.repository_creation_finished` with the outcome `created`, `refused`, or `failed`. The repository registers once every step is done, and its outcome is `created`. A creation that stops at a step answers `create_failed`, registers nothing, keeps every folder, commit, and forge repository it made, and does not stop the entries after it. The `path` of an entry to create is where its path leads, as the worker's check read it, also when the creation was refused after it started or stopped at a step; a check that refused before it read the path leaves the path as the manifest gives it. Every path a worker gave is kept with each line break a space and each control character dropped. A check that refuses answers `refused` with its `reason` and its `refusal_code`, the code the worker gave, such as `remote_exists` or `gh_timeout`, and creates nothing; `path_busy`, which only a preview's check answers when another creation on the worker holds the path, says in its `remedy` to preview again when that one finishes, and is never a failed creation, while an approval's check waits for that creation, as its creation does, and then creates; an entry refused for any other reason has no `refusal_code`. Each outcome of such an entry carries `creation`: the `forge`, `owner`, `forge_name`, `visibility`, and `default_branch`, the `url` the creation adds as `origin`, the `login` of the forge account, the first `commit` and its `commit_error`, each step's outcome in `steps`, the commands in `remaining` that finish a failed creation by hand, the `remedy` that fixes a refusal, which for a repository that exists on the forge, as when an earlier creation timed out after the forge made it, is to clone it where the entry's path leads and write `remote` in place of `create` in the manifest, and, once created, the `makefile` entry to add to the `REPOSITORIES` list of the workspace `Makefile`, as `name=<url>=<manifest path>`. The call runs to its end when its client disconnects, and deciding an approved version again answers with what the first decision recorded and creates nothing. A real run holds the registration for at most 10 minutes: when that time is up, the entry in progress ends as an error of the creator does, so its creation stays started with no finish and a retry can run it again, nothing more registers, each later entry is `not_attempted`, and `repositories_problem` says the run passed its limit. Every text the worker gave, a refusal's reason, a step's detail, and a command that remains, is kept and shown on one line with no escape sequence or control character. A daemon whose worker creates no repository refuses such an entry and says so. When a failure of the ledger or of the worker's checkouts stops registration part way, each repository the manifest lists after the one it stopped at has the outcome `not_attempted`, and a later approval of a new version or `repository add --manifest` registers it. `POST /v1/projects/{project}/adoption/plan` reads the layout around a clone on the machine of the daemon's worker and answers the plan of adopting it, and records nothing. The answer is the plan, with `parts` beside it: the digest of each part of the plan, by part name, which a client that cannot compute them sends back in the `restructure` of the work it creates. The parts are no part of the plan, and its `digest` does not hold them. It needs a member's session, and a delegate's call answers 403 `member_only`. It takes `{"root", "paths", "depth", "planning", "design", "leave_out"}`: `root` is the absolute path of the clone adopt runs in, `paths` are absolute paths of clones or of folders that hold clones, `depth` is how many levels below a folder to search, one by default and at most 4, `planning` and `design` name a repository by its clone's folder name, and `leave_out` names code trees of the design repository, relative to its top. `"practices": true` asks that each repository the plan would register be read for its practices, in process on the daemon's machine, at the base branch a registration would record, as the clone last fetched it from `origin`, with no forge binding, the default merge authority, and a scan of the whole history, which has 30 seconds for each repository; it records nothing. Each `repositories` entry then holds the check's result as `practices`, or, for a clone the check could not read, a `practices_note` that says why, or that the check did not finish in time, and names no path, and the answer carries `guides`: the practice table's `why`, `fix`, `template`, and `command` for each practice a finding names, by practice ID. The practices are no part of the digest or of any part. The answer holds the `layout` (its `root`, the `folders` the root ignores that hold clones, and each clone with its `where`, `plan`, `documents`, and `instructions`), the `shape` (`single`, `planned`, `consolidate`, or `workspace_files`), the `planning` repository (with `undecided` true and no name when the layout settles none), the `design` repository with its first-parent `root` and why, each `repositories` entry with its `outcome` (`registered`, `known`, `refused`, or `not_registered` for a design repository a consolidation imports), the `files` it would add, the paths a consolidation `takes` from the design repository, the `collisions` with the version kept, the `code_trees`, the `moves` as commands, `notes`, and the `digest`: the SHA-256 of the plan's JSON without the digest, the notes, and what a registration said of each repository, which the registration changes. `POST /v1/adoption/plan`, on no project, answers the same for a project the adoption has yet to create, with `new_project` true: it reads no record of any project, so each repository reads as one that would register. A daemon that reads no worker's clones answers 501 `unavailable`.

`POST /v1/projects/{project}/repositories/{repository}/remove` takes a repository out of the project once no open work order targets it, and answers 409 `repository_state` while one does; the record stays as history with state `removed`, and another project may then register it.

`GET /v1/projects/{project}/outside-edits` reads, for each active repository, its clone on the machine of the daemon's worker, and answers what the clone holds that intake and lanes cannot read (FR-UI-14). Each entry of `clones` gives the repository's `repository` and `name`, `planning` for the planning repository, the clone's `path`, the `branch` it has checked out, its `head`, and the `remote` a push goes to, and `problem` for a clone the machine keeps none of or git cannot read. `edits` lists each path, at most `limit` of them in order of path, with its `state`: `uncommitted` for a tracked path the working tree or the index changed, `untracked` for one git does not track and the clone does not ignore, and `unpushed` for one that a commit of the checked-out branch changed which no branch of the remote holds. `cut` says git listed more. Each path's `steps` are the kinds of the clone's `steps` that take it, and `hidden` marks a path that holds a character a page cannot show as a shell reads it, which no step names. Each step has its `kind`, `commit`, `push`, or `copy`, a `title` and `detail`, the `branch` it makes or pushes, the `paths` it takes, and the exact `commands`, one line each, to run on the clone's machine in POSIX sh, bash or zsh. A push names the branch in full on both sides, `refs/heads/<branch>:refs/heads/<branch>`, so it never forces, and a path or name that holds a backslash is named in no command. Every name, path, and problem is plain text. The read fetches nothing and changes no ref, index, or file, and a group server, which keeps no clone, answers 503 `repository_reads_unavailable`. `conflicts` lists each open work order whose lane's branch in the clone changed paths a person changed too, as the `needs-you` view lists it below.

A lane whose branch changed a file a person changed too is one item of the project's `needs-you` view, of kind `conflict`, with the work order's ID and the time a reading of this daemon first found it (FR-UI-14). The person's side is a path the clone holds uncommitted, untracked, or unpushed, or a path that commits on the remote's copy of the base branch changed since the branch and the base last shared a commit, counting only the commits on the base's first-parent line that are no merge, carry no `Ropeshift-Work-Order` trailer, and are neither the merge commit nor the head of a pull request the ledger records as merged, nor in a range of the base's first-parent line that the ledger records as written by a merge. Every commit a merge that ropeshift makes with git carries the trailer. A rebase that ropeshift makes on the forge reports the base's tip before it and after it, and the ledger keeps them with the merge as that range when it ends at the merge commit, and reads it only when its first end is an ancestor of its last. A pull request a person merges on the forge records no range, and in a repository whose merge method is `rebase` the base's side is not listed while the merge commit of a merged pull request with no usable range lies between the lane's branch and the base. The lane's side is what the branch's commits changed since that commit. The daemon reads them each time it reads the clones, on every intake tick and on each read of `outside-edits`, and it never fetches. Its `conflict` holds the `work_order` with its `title` and `state`, the `lane`, its `branch`, the `base` it was read against, such as `origin/main`, the `repository` and its `name`, the `clone` path, each of the `paths` with its `person`, `uncommitted`, `untracked`, `unpushed`, or `pushed`, and `hidden` for one no command names, `cut` when git listed more paths than a reading keeps, the `options`, `keep_both`, `keep_person`, and `stop`, each with its `title`, `detail`, and exact `commands` for POSIX sh, bash or zsh, and `clears`, which says what ends it. `keep_both` commits the clone's files on the branch `edits/<work order>-<digest>`, named by a digest of the files and what they hold, so the name stays the same while the files do. Ropeshift runs none of the commands and resolves nothing. The item leaves once a reading no longer finds both sides changing a path, once the lane's branch holds that edits branch and the base's commits, once the lane's branch is gone from the clone, or once the work order leaves the states in which its branch holds unmerged work. A reading that could not read the clone or the branch, or whose context ended, keeps the item it found before, with the time it was first found, and a reading that began before another replaces nothing the newer one found. The items are held in the daemon's memory: a restarted daemon lists them again once its first intake tick, which runs at start, reads the clones, timed from that reading. On a solo daemon, `outside-edits` answers from a reading that began within one intake tick. `outside-edits?fresh=1` reads the clones again whatever that window holds, and the reading it makes is the one the next read within the window answers. A project runs at most one such reading at a time and one waits for it, so the calls that arrive while one runs share the next, which begins after they arrived. A reading that takes longer than 2 minutes ends in an error. Any other query is refused with 400 `invalid`.

`GET /v1/projects/{project}/practices` answers the practices check's latest result of each active repository, by name, or of the one `?repository=` names by name, identity, or a prefix of it, with 404 `not_found` for one the project does not hold. Each entry holds the repository's `name` and `repository`, the `result` once a check reported, and the open `request` while one is offered and has not expired. A result holds the `request` whose report made it the latest, the `commit` it read, its `base_branch`, the `worker`, `checked_at`, `table_version`, `rules_version`, `scanned_from`, `skipped`, `partial`, and `truncated`, each of the twelve practices in table order as `practices`, and the `findings`. A practice holds its `id`, `severity`, `status` (`met`, `finding`, `unknown`, or `not_applicable`), a `reason` for the last two, `why` it matters, its `fix`, its `template`, and the `command` that prints the template, `ropeshift template show <template>`, which is absent for a practice with none. A finding holds the same words and its `id`, `practice`, `subject` (what the practice found wanting, which is part of the ID and absent for a practice with one finding), `severity`, and `detail`, and for a `secrets` finding its `rule`, `path`, `line`, `commit`, and `digest`, never the matched text. `acknowledgement` lists the findings a member acknowledged, each with its `finding`, `reason`, `member`, and `acknowledged_at`, and is absent while none is. A finding of the result that a member acknowledged stays in `findings` and reads `acknowledged` true with its `acknowledgement`, and its practice stays `finding`: nothing is filtered out. `POST /v1/projects/{project}/practices/checks` takes `{"repositories": [...]}`, each a name, an identity, or a prefix, and an empty list names every active repository. It asks the worker that keeps each repository's checkout, the daemon's own first, to run the check, and answers 202 with `checks`, one entry for each repository in the order named: its `repository` and `name`, and either the `request` offered, with `existing` true when the repository already had that request open and none was made, or the `reason` none was, such as "no connected worker keeps a checkout of widgets" or "worker NAME speaks protocol N; upgrade it to run the practices check". A name the project does not hold answers 404 and requests nothing. It needs a member's session, and it is the operational operation `practices.check`, so a delegate's call runs as the delegate. `GET /v1/projects/{project}/practices/checks/{request}` answers a request with its `id`, `repository`, `worker`, `worker_name`, `cause` (`registration`, `planning_session`, or `member`), `requested_by`, `requested_at`, `expires_at`, `reported_at`, and its `state`: `offered`, `reported`, or `expired`, which an offered request reads as once its expiry passes. A request that expired and is reported later still records its result. Registering a repository, recording a planning session's work order, and starting the session that revises a plan each request a check too, with the cause that names them, and a request that cannot be made leaves the registration or the session as it was. No finding blocks a claim, a lane, a review, a merge, a plan's approval, or an adoption.

`POST /v1/projects/{project}/practices/acknowledgements` takes `{"repository": ..., "finding": ..., "reason": ...}`, the repository by name, identity, or a prefix of it and the finding by the ID a result lists, and keeps the member's reason for leaving that finding open. It answers 201 with the acknowledgement (`finding`, `reason` without its padding, `member`, `acknowledged_at`) and appends `practices.acknowledged`, which holds the finding, the repository, the reason, the member, and the time. The reason is stored redacted and on one line: the shapes of credentials are taken out, and each line break, tab, and other control character becomes a space, so what the answer, the read, the event, and a card hold is that text, held to 2 KiB. It answers 400 `invalid` for a body that is not those fields, an empty reason or one that is empty once its control characters are taken out, a reason over 2 KiB as given, a finding ID that no practice's grammar allows, and a finding ID over 2000 bytes or with a control character, 404 `not_found` for a repository the project does not hold or removed and for a body that names none, and 409 `acknowledged` for a finding the repository already holds an acknowledgement of, which a withdrawal removes first. A finding no result holds may be acknowledged, because a check may not have run since it appeared; the read lists it in the repository's `acknowledgement`. `POST /v1/projects/{project}/practices/acknowledgements/withdraw` takes `{"repository": ..., "finding": ...}`, removes the acknowledgement, answers 200 with the acknowledgement it removed, and appends `practices.withdrawn`, which holds the reason that was withdrawn and who gave it, and answers 404 `not_found` for a finding with none. A withdrawal answers 400 `invalid` for a body that is not those fields, an empty finding ID, one over 2000 bytes, and one with a control character, and holds the ID to nothing else, so an acknowledgement of a practice a later table removed can still be withdrawn; it answers 404 `not_found` for a repository the project does not hold, for a body that names none, and for an ID with no acknowledgement. Each needs a member's session. They are the consent operations `practices.acknowledge` and `practices.withdraw`, which no delegate policy exempts, so a delegate's call, the assistant's included, answers 202 with a confirmation card that names the finding, why its practice matters, and the reason, bound to that finding, and a member's confirmation runs the call as that member. Both change what a member sees as open and nothing else: no claim, lane start, review, merge, plan approval, or adoption reads an acknowledgement or a finding. The web listener serves every practices route above, and each change needs a member's session and the CSRF token ([the web UI](web-ui.md#practices)).

`POST /v1/projects/{project}/backup` copies one project's ledger, and `POST /v1/installation/backup` copies the installation database. Each takes `{"path": "..."}`, an absolute path on the daemon's machine where no file exists, and needs a member's session. `POST /v1/projects/{project}/backup/download` and `POST /v1/installation/backup/download` take `{}` and answer the same copy in the response, as `application/vnd.sqlite3` with a file name in `Content-Disposition`, for a browser that saves it as a download; nothing of it stays on the daemon's machine.

`GET /v1/audit` reads the installation's log, and `GET /v1/projects/{project}/audit` a project's, newest first: each event with its revision, type, actor, subject, times, and its whole record. `actor` keeps one actor kind, `actor_id` one actor's ID, `kind` the event types that start with its text, `subject` one subject kind, `limit` sets the page from 1 to 200 (50 by default), and `before` starts the page below a revision, which the answer's `next` names, zero when no older event is left. A filtered read looks at 5,000 events at most and answers `"scanned": true` with `next` where it stopped. `GET /v1/members` lists each member that holds a live session, with when each session began and ends, and how many members can sign in; no answer carries a session's token.

A change to a record every project shares, such as a member's sign-in, a worker's registration or autonomy, or an orchestrator, records its event in the installation's log, and no project's log holds it.

`PUT /v1/passphrase` sets the passphrase. On the socket it takes `{"passphrase": "..."}` of 8 to 1024 bytes: the first needs no session, and a later one needs a member's session, and a body that names a current passphrase is refused with 400 `invalid`. It answers 200 with `{"sessions_ended": N, "delegates": N}`. A later set ends every session of the member in the transaction that stores it, the one the call came from included, because the socket has no cookie to carry a new token: `sessions_ended` counts the others, and `delegates` the member's delegate credentials that still act. The first set ends none. The web listener serves the route only as a change, and takes `{"current": "...", "passphrase": "..."}` with a live session, the token its own page holds, and the passphrase in force. It answers 200 with `{"sessions_ended": N, "delegates": N}`: the member's other sessions that the change ended in the same transaction, and the member's delegate credentials that still act, which it leaves alone. The session the change came from goes on under a new token, which the answer sets in new `ropeshift_session` and `ropeshift_csrf` cookies, and the old token opens nothing. It answers 401 `bad_passphrase` for a missing or wrong `current`, the same answer for each, 401 `not_enrolled` while no passphrase is set, 409 `passphrase_changed` when another change landed between the check of `current` and the write, and 400 `invalid` for a new passphrase outside the bounds, which it says only once `current` has proved the caller ([authorization](authorization.md#changing-the-passphrase-from-the-web-ui)).

## Spend

`GET /v1/projects/{project}/spend` reads where a project's spend stands. It answers `project`, the project's spend policy in force, and `installation`, the installation's, each with its `version`, `authored_by`, `created_at`, and `keys`, a list of `{"key": "...", "value": "..."}` that names each key as `ropeshift spend set` does, such as `no_history_limit.medium`, and gives its value as text. `work_orders` lists each open work order a limit covers with what `GET /v1/projects/{project}/work-orders/{id}/spend` gives for one: its `charged` spend, `{"recorded_usd", "estimated_usd", "estimated_turns", "unpriced", "charged_usd"}`, a `label` that says it is estimated at list price and with how many turns estimated by average, `soft_limit` and `hard_limit` in US dollars with 0 for none, `basis`, which is `baselined_band`, `current_band`, `no_history`, or `review`, `remaining` to the hard limit, `raised_to`, the limit a member raised it to when that is the limit in force, `conditions`, which hold `over_estimate` once charged spend reaches the soft limit and `spend_limit` once it reaches the hard limit, and the `policy_version` the limits were derived under. A work order the project does not hold answers 404 `not_found`. These are reads for a member and for a delegate. A lane, a worker, and an orchestrator read none, and nothing a lane or an orchestrator reads holds a band, a limit, or what remains.

`GET /v1/projects/{project}/spend` also answers `project_spend`, what the project's lanes were charged today and this week against its daily and weekly limits. Its `day` and `week` each hold `window`, `spent_usd`, `soft_limit` and `hard_limit` in US dollars with 0 for none, `raised_to` when a member raised the window's limit, `remaining`, and `starts_at` and `ends_at` in milliseconds since the epoch. A day is the UTC calendar day and a week starts on Monday at midnight UTC. A window whose `spent_usd` has reached its `hard_limit` holds the project: no work order of it is claimed until `ends_at`, and a claim answers 409 with the limit and when work goes on.

`POST /v1/projects/{project}/spend/project/raise` lifts the project's daily or weekly limit for the window it is made in. It takes `{"window": "day", "by_percent": 50}` or `{"window": "week", "to_usd": 200}`: the window, `day` or `week`, and exactly one of the percentage and the amount. It answers 200 with what the ledger recorded, `{"window", "window_start", "before_usd", "after_usd", "spent_usd", "by_percent", "to_usd", "policy_version"}`, and evaluates the lanes the project's limits parked in the same transaction, so a lane whose project is now under its limits wakes once. A raise ends with its window: the next day or week runs on the limit the spend policy holds. It may name `window_start`, the start of the window it asks for in milliseconds since the epoch, and a raise for a window that is over answers 400 `invalid` and says so; a delegate's card carries it, so a card confirmed in a later day or week lifts nothing. A body that names neither or both, a window that is not `day` or `week`, a limit that is not higher than the one in force or not above what the window was charged, an amount past 1,000,000, and a window with no limit set answer 400 `invalid`. It has the authority of a work order's raise: a member's session raises, a delegate's call answers 202 with a confirmation card that shows the limit before and after and that no delegate policy exempts, and a caller with no member's session, an orchestrator and a lane included, answers 401 `session_required`.

`POST /v1/projects/{project}/work-orders/{id}/spend/raise` lifts a work order's hard limit. It takes `{"by_percent": 50}`, a percentage of the limit in force, or `{"to_usd": 80}`, an amount in US dollars, and exactly one of the two. It answers 200 with what the ledger recorded, `{"work_order", "act": "raise", "before_usd", "after_usd", "charged_usd", "by_percent", "to_usd", "policy_version"}`: the limit before and after, and what the work order had been charged. The limit in force is the larger of the one its band derives and the highest a member raised it to, so a raise is never lowered by a new version of the spend policy. A body that names neither or both, a limit that is not higher than the one in force, a limit that would stay at or below what the work order is charged (the message says "would stay below charged spend" and gives the figure, because a raise that clears nothing wakes a lane only to stop it again), an amount past 1,000,000, and a work order with no hard limit or one that is done or canceled answer 400 `invalid`, and a work order the project does not hold answers 404 `not_found`. `POST /v1/projects/{project}/work-orders/{id}/spend/resume`, with an empty object, grants one more generation's allowance: it lifts the limit to what the work order is charged plus the mean charge of its generations that recorded spend, and the answer records the limit before and after as a raise does, with `allowance_usd` and `allowance_basis` (`mean_generation`). Work with no generation that recorded spend is sized by its estimate instead (`estimate`), and work with neither answers 400 `invalid` with a message that says to raise its limit with `ropeshift spend raise`. It takes work a hard limit parked, and answers 400 `invalid` for any other. Each, and a new version of the spend policy, evaluates the lanes parked on the work order's limit in the same transaction, so a lane whose work order's limit is now above what it was charged wakes once. A member's session raises and resumes. A delegate's call answers 202 with a confirmation card that shows the limit before and after, which no delegate policy exempts, and a caller with no member's session, an orchestrator and a lane included, answers 401 `session_required`. A delegate's raise by a percentage is a card for the amount it comes to when it is asked, such as `{"to_usd": 37.5}`, so a member who confirms it later lifts the limit to that amount and no further, whatever the limit has become.

Work at its hard limit refuses every act that would start more spending on it, whoever asks: `POST /v1/projects/{project}/work-orders/{id}/retry`, `.../lane-reset`, and `.../lane-respawn` answer 409 `spend_limit`, with a message that names the work order, its limit, what it is charged, and says to raise it with `ropeshift spend raise`. A delegate's `.../lane-resume` of a lane that waits on the limit answers 403 `forbidden`: only a member ends a spend stop.

A member also ends a spend stop without lifting its limit. `POST /v1/projects/{project}/work-orders/{id}/spend/block`, with an empty object, blocks the work order with the reason `spend_limit`, and `.../spend/replan` sends it to `planning`, where its contract passes review again. Each ends the lanes the stop parked and retires their wakes in the transaction that moves the work order, so a raise later wakes nothing, and each answers 200 with `{"work_order", "state", "reason": "spend_limit"}`. Each takes work a hard limit parked and answers 400 `invalid` for any other, and for a replan of a review, which has no contract to plan again and is blocked instead, discarding its lane's worktree, and 404 `not_found` for a work order the project does not hold. A member's session blocks and sends to replanning, a delegate's call answers 202 with a confirmation card that shows the work order leaving `parked`, which no delegate policy exempts, and a caller with no member's session answers 401 `session_required`. A blocked work order leaves as any blocked work does, through `.../resolve` or `.../replan`.

A lane held on its own settings is one item of the `needs-you` view, of kind `lane_settings`, whose `lane_settings` holds the lane, its `work_order`, the `category` `security`, the `change` it is held on (`files`, `keys`, `summary`, `digest`, and `scripts`, the files a hook, a status line, or a file suggestion command of the repository runs that the lane changed), the `recommendation` with its `recommendation_rationale`, and the `actions` it offers ([when a lane changes its own settings](authorization.md#when-a-lane-changes-its-own-settings)). A member answers it with `POST /v1/work-orders/{id}/lane-settings`, taking `{"lane", "digest", "choice"}`, where `choice` is `base`, `lane`, or `stop`, and it answers 200 with `{"work_order", "state", "choice"}`. A hold that names any `scripts` offers no restore: its `actions` leave out `settings_base`, it recommends `stop`, and a `base` choice answers 409 `settings_not_restorable`. A digest of another change answers 400 `invalid`.

A work order a hard limit parked is one item of the project's `needs-you` view, of kind `spend`, with the ID `<work order>:spend_limit` and the time it parked, however many lanes served it. Its `spend` holds the `work_order`; its `spend` figures as `.../spend` answers them, with `charged`, `soft_limit`, `hard_limit`, `remaining`, and `basis`; the cost `band` with its `p50`, `p85`, `outcomes`, and `confidence` when the work order has an estimate; `resume`, what Resume once would do now, with `allowance_usd`, `basis`, and the `limit_usd` it sets, absent when nothing sizes one more generation; `lanes`, each lane that served the work order with the digest of its last generation that sent one and its last handoff, whose `narrative` is absent when the handoff degraded; `waiting_share`, absent while no model call has been attributed as waiting or working; and `actions`, which lists `spend_raise`, `spend_resume` only where `resume` is present, `spend_block`, and `spend_replan` except for a review, which has no contract to plan again. The item replaces the resume and long-parked items a parked work order would raise, and it leaves the view once a raise lifts the limit above what the work order is charged, or the stop is blocked or sent to replanning. Each time a hard limit parks a work order's lane is one interruption in the product measures, and no act on the stop counts another. A list an agent left out of a lane's narrative, and a digest's `files_written` when it lacks one, read as empty arrays, and a missing `tool_calls` as an empty object, so none is null.

A spend setting changes by publishing a policy, through `POST /v1/projects/{project}/policies` with `{"body": "..."}` as every policy does. A body whose table is `[spend_policy]` publishes the project's spend policy, and one whose table is `[installation_spend_policy]` publishes the installation's, which the same route keeps with the autonomy policy. A body states its `version`, which must be newer than the one in force, and every key of its table: a key left out, a key the table does not have, or a value outside its range answers 400 `invalid` with the key named, and changes nothing. `GET /v1/projects/{project}/policies?kind=spend` and `?kind=installation_spend` list the versions, newest first, and `GET /v1/projects/{project}/policies/{version}?kind=spend` reads one, which is the history a revert reads: a revert publishes an earlier version's values as a new version. Only a member's session publishes. A delegate's call answers 202 with a confirmation card that shows the policy before and after, which no delegate policy exempts, and a caller with no member's session answers 401 `session_required`.

## The project templates

`GET /v1/templates` lists the project templates the daemon's binary embeds, and needs no session. It answers `version`, the build version of the daemon's binary, and `templates`, one for each template, sorted by name. Each has `name`; `shapes`, the shapes of `ropeshift new` that write it, in the order `workspace`, `monorepo`, `repository`, and empty for a template no shape writes; `writes_to`, the path the template's file has in a new project's folder, `profile.toml` for the user profile, which `ropeshift init` writes to the state directory, and empty for a template nothing writes; and `content`, the text `ropeshift template show` prints, rendered for the example project. A daemon started with no templates answers 501 `unavailable`. `ropeshift template show` reads this route when `version` equals its own, and the web UI's Templates view reads it.

## The combined Needs you

`GET /v1/needs-you` lists what waits on a member in every active project, the longest wait first. Each item is the item a project's `needs-you` view holds, with a `project` that names its project's ID, name, and display name. Each item has a `tier`, how much it holds, which the web UI sorts by before the wait: `1` holds a running session (a `tool_call` or `artifact` approval a lane waits on, and a batch with a blocking question), `2` is stopped work (stuck, failed, or parked work, a `recovery` approval, an uncertain effect, a spend stop, CI that asks a person, a repository creation, and a `conflict` that holds a lane's merge until a member settles it), `3` waits for a decision (everything else, a kind a client does not know included), and `4` can wait (a design history check). Each question of a `questions` item has `asked_by`, who asked it, and `lane`, the lane that asked it, absent when no lane did. A lane's request has `gate` set when its call is one the lane's profile gates, or a push, which the worker that raised it marks, and which a member approves one call at a time. `projects` lists each active project with the revision its ledger stood at and how many of its items wait. A member acts on an item through its own project's routes.

A merge request is an approval of kind `merge`. Its `detail` is JSON that names the work order by `work_order_id` and by its `title`, the repository, the reviewed `commit`, the `branch` and its `base`, the `pull_request` number and its `url` when the work lands through one, the merge `method`, and the `merge_authority`, and for a held merge the `reason` it stopped and the `request` it answers. A request raised before `title` existed has none.

## Delegates and confirmation cards

A delegate is an agent outside ropeshift acting with a member's delegate credential ([authorization](authorization.md#delegation)). It sends the credential in the header `Ropeshift-Delegate`, on the local socket only. Its actor is `delegate`, with the ID `<member ID>/<credential ID>`, so every event it causes names the member it acts for.

A member's session manages the member's own credentials, on the installation's routes:

| Route | Body | Answer |
|-------|------|--------|
| `GET /v1/delegates` | | `{"as_of", "delegates": [...]}`: each credential the member made: its `id` (`dlg_<ulid>`), `label`, `project`, `kind` (`external`), `created_at`, `expires_at`, `last_used_at`, `revoked_at`, and `state` (`active`, `expired`, or `revoked`) |
| `POST /v1/delegates` | `{"project": "...", "label": "...", "expires_in_ms": N}` | 201 with the credential and its `token`, the one time anyone sees it. `project` names an active project, `label` is 1 to 64 characters, holds no control, format, or separator character (a zero-width space, a byte order mark, and a bidirectional control are refused), is kept in its Unicode compatibility-normalized form, and is never `assistant`, in any case and with spaces around it, which is the assistant's own credentials' label (a refusal is 400 `invalid`), and `expires_in_ms` is from one minute to thirty days |
| `POST /v1/delegates/{id}/revoke` | `{}` | The credential, revoked |
| `POST /v1/delegates/{id}/remove` | `{}` | 204, once the credential no longer acts, and 409 `delegate_active` while it does |
| `POST /v1/sessions/end-all` | `{}` | `{"sessions", "delegates", "conversations"}`: every session of the member ends and every credential of theirs that acts is revoked, in one transaction with one event, and then every running conversation of theirs with the assistant stops, in every active project |
| `GET /v1/operations` | | The class table: each operation's `id`, `label`, `class` (`operational`, `consent`, or `member_only`), `exemptable`, and `never_reason` |

The ledger keeps a credential's digest and never its token, and each change to one is an event in the installation's log with the member as its actor. A call that acts records the credential's last use when the one it holds is more than a minute old, as a `delegate.used` event.

These refusals are a delegate's:

| Status | Code | When |
|--------|------|------|
| 400 | `invalid` | A request carries both `Ropeshift-Session` and `Ropeshift-Delegate`, or a consent call carries no `Ropeshift-Why` |
| 401 | `bad_delegate` | The credential is not known, was revoked, or expired, which the message names |
| 403 | `outside_project` | The route is an installation route, or another project's |
| 403 | `member_only` | The operation is a member's alone, such as every route above, a delegate policy, or a card's decision |
| 409 | `delegate_active` | A removal of a credential that still acts |
| 403 | `forbidden` | Any request to the web listener that carries `Ropeshift-Delegate` |

Every changing route names its operation, and a delegate's call takes the operation's class. An operational call runs as the delegate. A consent call runs as the delegate only when the delegate policy in force exempts it, and then records a `delegate.exempted` event naming that policy's version. Any other consent call runs nothing: it records a card, an approval request of kind `confirm`, and answers 202 with `{"card": <approval>}`. It needs the header `Ropeshift-Why`, the delegate's reason, up to 2,000 characters. A call that would make work, a question, or a decision by an `id` that is not plain, or a decision by an `id` that starts with `pd-`, answers 400 `invalid` before it becomes a card, because a card names its record by that ID. A call that resolves to several operations, such as a repository change that sets several fields, takes the strictest class, and is exempt only when every consent operation in it is.

A call that makes a work order takes its class from the credential that makes it, because an orchestrator's wake states a work order's title. An outside delegate's `POST /v1/projects/{project}/work-orders` is the consent operation `work_order.create`, whose card names `work_order:<id>` from the body and binds to the call's arguments, and its `POST /v1/projects/{project}/plans/{id}/reviews` is `plan.start_review`, whose card names `plan:<id>` and binds to the plan as it stands, so a plan that changes before the confirmation makes the card void. Nothing is created until a member confirms the card, unless the delegate policy exempts the operation. The assistant's same calls are the operational `work_order.create_by_assistant` and `plan.start_review_by_assistant`, which run at once, and a member's run as they always did. An orchestrator's wake and its tools' replies state the text of work, a question, a decision, or a contract a delegate made, the assistant's included, between `<delegate_text>` tags ([authorization](authorization.md#who-can-do-what)), and so is the text of one a member made by confirming a delegate's card, whose creation event names the delegate as its proposer.

A card holds:

| Field | Holds |
|-------|-------|
| `subject` | `<kind>:<id>` of the record the call names |
| `subject_digest` | What the card binds to: the SHA-256 of the record's kind, ID, and the revision of the newest event about it; for a decision of a request, that request's own digest and state; for a policy, the version in force; for a call that creates its record, its arguments, so such a card never goes void |
| `summary` | The operation's label and the subject, such as `Raise merge authority: web` |
| `requested_by` | `delegate:<member ID>/<credential ID>` |
| `detail` | JSON with `operation`, `label`, `method`, `path` (the full project-scoped path), `arguments` (the body as sent), `why`, and `changes`: `{field, from, to}` per field for a repository change or the fleet's caps, where a `to` of null says the call removes the field's value, as a withdrawal does and the web card shows as removed, `{before, after}` bodies for a policy or a roster change, and `{field, to}` per argument for any other call |

A member decides a card with `POST /v1/projects/{project}/approvals/{id}/decide`, passing the digest they read. Declining, with `"allow": false`, makes it `denied` and runs nothing. Confirming binds the subject again: one that moved makes the card `void` and answers 409 `stale_digest`. Otherwise the card is `approved`, and its exact call runs through the project's own routes as that member's session, with the same checks and events as the member's own call, and each event it records names the member as its actor and the delegate that prepared the card as its proposer. A 2xx answer makes the card `used`, and any other makes it `failed`, with the API's refusal as its `reason`. `decided_by`, `decided_at`, and `channel` (`web` or `cli`) say who confirmed it, when, and where. The call runs, and its outcome is kept, even when the member's client goes away before the answer. A card still `approved` ten minutes after its confirmation lost its call to a crash, and a sweep makes it `failed` with the reason `interrupted; check the audit`: the project's audit says whether the call ran. A card has `expires_at` 0, and nothing expires it. A delegate's decision of a card answers 403 `member_only`.

Revoking a credential, or signing out of every session, voids the open cards it prepared, and a confirmation of a card whose credential was revoked or removed voids it and answers 409 `request_closed`. A delegate holds at most 20 open cards in a project: its next consent call answers 403 `forbidden` until a member decides one.

| Card state | Means |
|------------|-------|
| `pending` | Open: it waits for a member |
| `approved` | Running: a member confirmed it, and its call is running |
| `used` | Confirmed: its call ran |
| `failed` | Failed to run: the API refused its call |
| `denied` | Declined |
| `void` | Its subject changed before a member confirmed it |
| `expired` | Expired |

The combined Needs you lists each pending card of every active project as an item of kind `confirm`, with a `card` that holds the approval, its parsed `detail`, and the preparing delegate's `label` and `member`. A card also holds `delegate_kind`, `external` or `assistant`, which a surface shows the card's preparer by, never its label. A card the assistant prepared also holds `conversation`, the `id` and `name` of the conversation it came from; once that conversation is deleted, `name` is empty and `deleted` is true, and the card stays. `GET /v1/projects/{project}/approvals/{id}` answers the same `conversation` beside the approval's fields.

A card the assistant prepared stays confirmable after its session stops, because its credential ends with each generation and that says nothing against what it prepared. Revoking that credential by its ID, or signing out of every session, voids its open cards as it voids any delegate's.

A delegate policy is a versioned policy of kind `delegate`, published with `POST /v1/projects/{project}/policies` as a member, and listed with `GET /v1/projects/{project}/policies?kind=delegate`:

```toml
[delegate_policy]
version = 2
exempt = ["work_order.accept", "work_order.rework"]
raise_model_and_effort = false
```

`exempt` lists consent operations by ID, and may list only `work_order.accept`, `work_order.rework`, `work_order.create`, and `plan.start_review` ([authorization](authorization.md#delegates)). A call to `POST /v1/projects/{project}/work-orders/{id}/accept` is `work_order.accept` only for work whose review has ruled on its attempt and whose every criterion passed on a check the lane did not write, with no check failed, no verdict that counts for the attempt `fail` or `cannot_judge`, and every check its base requires green on its pull request, as the work stands when the call comes, and `work_order.accept_unverified` otherwise. A change or a rework that completed at a commit has a review of that commit, which has ruled once no review of the attempt is open and verdicts count for it. A call to `.../rework` is `work_order.rework` only once a verdict that counts for the attempt failed, and `work_order.rework_without_failed_verdict` otherwise. A version that lists an unknown ID, an operational or member-only operation, or an operation that is never exempt answers 400 `invalid`, naming each and why. The built-in version exempts nothing, and a version published before the list narrowed exempts nothing outside it.

`raise_model_and_effort` says whether a delegate's lane start may raise the lane's model or effort above what the lane would run without its overrides ([authorization](authorization.md#delegates)). It is `true` or `false`, and any other value answers 400 `invalid`. A version that leaves it out allows the raise, as the built-in version and every version published before the setting do.

A policy body of any kind spells each key one way. `POST /v1/projects/{project}/policies` answers 400 `invalid` to a body that holds two keys of one table that differ only in case, such as `raise_model_and_effort` and `Raise_Model_And_Effort`, or `[delegate_policy]` and `[Delegate_Policy]`, naming both, and publishes nothing: the decoder reads a key whatever its case, so it would take either. A table inside an array of tables is a table of its own, so `command_prefix` and `Command_Prefix` in one `[[delegation_policy.classes]]` entry are refused too, and the refusal names the entry.

An event's `actor_for` and `actor_label`, in the event stream and the audit, name the member a delegate acted for and its credential's label, or the credential's ID once its record was removed, and `delegate_kind` names its kind, `external` or `assistant`, until its record is removed. They are absent for every other actor, and `GET /v1/audit?actor=delegate` keeps a delegate's events. An event a confirmed card's call recorded also holds `proposer_kind` (`delegate`) and `proposer_id` (`<member ID>/<credential ID>`), naming the delegate that prepared the card, and they are absent from every other event.

## Conversations

A member talks to one target at a time: their assistant in a project, the orchestrator of a worker that serves the project, a planning session, or a lane ([authorization](authorization.md#delegation)). Every route here is a project's, under `/v1/projects/{project}/`, and needs a member's session; a delegate reads its member's conversations and changes none.

| Route | Body | Answer |
|-------|------|--------|
| `GET /v1/conversations` | | `{"as_of", "conversations", "workers"}`: the member's conversations, newest activity first, and each registered worker with `available` and, when it is not, `reason` |
| `POST /v1/conversations` | `{"id", "name", "worker"}` | 201 with `conversation` and `stopped`, the running conversation it stopped first. `id` is the client's, so a retry makes one; an ID another member's conversation holds, or a deleted conversation held, is refused with 400 `invalid` |
| `GET /v1/conversations/{id}` | | One conversation |
| `POST /v1/conversations/{id}/open` | `{"worker"}` | Starts its session, resuming what it had, with `stopped`, and sends nothing: it is the warm start a client makes on the member's first keystroke, so the session is up when the message goes |
| `POST /v1/conversations/{id}/stop` | `{}` | Stops its session; the conversation stays |
| `POST /v1/conversations/{id}/rename` | `{"name"}` | `name` is 1 to 80 characters |
| `POST /v1/conversations/{id}/delete` | `{}` | 204: its session stops, and its entries, its messages, and its record go in one transaction. Each worker that ran it then removes what it holds of it: the messages to it and its runs' records in its journal, and the directory its sessions ran in. Its actions' events and its cards stay in the ledger. The agent CLI's own record of a session, where the CLI keeps one, is outside ropeshift's control and stays |
| `POST /v1/conversations/{id}/compact` | `{}` | Asks its running session to compact its context with the runtime's own command, and adds a `compacted` marker |
| `POST /v1/conversations/{id}/clear` | `{}` | Ends its running generation and starts the next with an empty context, on the same worker, adds a `cleared` marker, and marks every earlier entry `before_clear`, which no later first prompt holds |
| `GET /v1/conversations/{id}/entries` | | A page of its entries |
| `POST /v1/conversations/{id}/messages` | `{"id", "body", "worker"}` | 201 with `conversation`, `entry`, `message`, and `stopped`: the member's message to the assistant, which opens a stopped conversation first and is delivered once its session runs |
| `GET /v1/conversation-targets` | | What the member can talk to now |
| `GET /v1/lanes/{id}/stream` | | A page of a lane's stream |
| `GET /v1/orchestrators/{worker}/stream` | | A page of a worker's orchestrator's stream in this project |

A conversation holds `id`, `member_id`, `name`, `worker_id`, `worker_name`, `desired_state` (`running` or `stopped`), `actual_state`, `run_lane`, `current_generation`, `stopped_reason`, `created_at`, `last_active_at`, and `open_cards`, the cards it prepared that wait.

| Actual state | Means |
|--------------|-------|
| `starting` | Its session was asked for, and its worker has not reported it running |
| `running` | Its session waits for the member |
| `working` | A turn is running |
| `stopping` | Its session was asked to stop, and its worker has not reported it stopped |
| `stopped` | It has no session |
| `failed` | Its session could not start, which `stopped_reason` names |

At most one of a member's conversations runs in a project: creating, opening, or messaging one stops the running one, with a `stopped` marker. A new conversation is called `New conversation` until the member's first message, which names it with its first 60 characters, cut at a word, unless the member named it. A conversation stops when it sits idle past the assistant policy's `idle_stop`, with an `idle_stopped` marker, and sooner, past its `warm_idle_stop`, while no member message has reached it since its session started or was cleared; closing a view or switching target stops nothing. Reading a conversation, its entries, the list, or the conversation targets starts no session: the history comes from the ledger. Another member's conversation answers 404 `not_found`.

A start runs on a worker that is connected, because its session opened or it last beat within three heartbeats, that holds a checkout of every active repository of the project, and that runs headless sessions. A start that names a worker takes that one. With none named, it takes the conversation's last worker while it can, else the only one that can; with several that can it answers 400 `invalid` ("Choose a worker: atlas and basalt can run the assistant."), and with none it answers 409 `no_assistant_worker`, naming each worker's reason.

These refusals are the conversation surface's own:

| Status | Code | When |
|--------|------|------|
| 409 | `no_assistant_worker` | No worker can run the project's assistant |
| 409 | `target_not_running` | A compaction or a clear of a conversation whose session is not running, or a message to an orchestrator that is not running |

A conversation's entries, a lane's stream, and an orchestrator's stream share one entry: `id`, `at`, `kind` (`member`, `reply`, `event`, `action`, `card`, `request`, `question`, or `marker`), `from` (`kind`, `id`, `label`, and a delegate's `delegate_kind`), `body`, `message` (a member's message, with its delivery state), `event` (with `actor_for` and `actor_label`), `action`, `approval` (the current approval of a `card` or a `request`), `question` (the current question, its batch, the `channel` a member's answer came through, and the `scope` and `scope_title` a read of questions gives), `marker`, `assent`, and `before_clear`. A page is `{"entries", "next", "as_of"}`: oldest first within the page, the newest page first. `before` takes a page's `next`, and `limit` is 1 to 500, 100 by default.

- A conversation's entries hold the member's messages, the assistant's replies, the operations it ran as `action` entries, a `card` entry in place of each card it prepared, holding the card as it stands now, and its markers (`started`, `stopped`, `compacted`, `cleared`, `idle_stopped`). A member's message that reads as a yes while a card waits carries `"assent": true`, and is still only a message.
- A lane's stream, for a headless lane or a planning session, holds the messages members and their delegates, the assistant among them, sent it, with their delivery state and the sender a `member` entry's `from` names, its replies, the events about the lane or its work order, its approval requests, and the questions it asked or is attached to.
- An orchestrator's stream holds this project's events its orchestrator caused, the member's messages to it with its replies, and the recovery requests it raised.

A request, a question, or a card resolved anywhere stays at its place in a stream, with its outcome.

`GET /v1/conversation-targets` answers `assistant` (the member's newest conversation or null, the `workers`, `idle_stop_ms`, and `warm_idle_stop_ms`), `orchestrators` (each worker that holds a checkout of an active repository of the project, with its name, state, `waiting_for` as the shop floor gives it, generation, and the projects it serves), `planning` (the lanes of planning and adopt work that have not ended), and `lanes` (every other lane that has not ended), each lane with its work order and title, worker, generation, run mode, and state.

`POST /v1/projects/{project}/messages` takes `"to": {"kind": "orchestrator", "worker": "..."}` beside a lane's `"to": {"lane": "..."}`; exactly the field of its kind is set. A message to an orchestrator answers 409 `target_not_running` while that orchestrator is not running, and 400 `invalid` when its worker serves no repository of the project. Only a member sends one: a delegate's call, the assistant's included, answers 403 `member_only` and records no card, because an orchestrator holds tools such as `approval_decide` and `lane_start`, and a body that does not say who the message is for takes that class too. An orchestrator's own `reply` is not a message and stays. It reaches the orchestrator as one item of its next wake, with its age, moves to `at_worker` when the worker takes it, `handed_off` when the wake reaches a turn, and `replied` when the orchestrator replies, and it expires on the message window like any other. A message to the assistant goes through its conversation, and `"kind": "assistant"` here answers 400 `invalid`. A message to a lane takes its class from the credential that sends it, because it steers what the lane does next: an outside delegate's is the consent operation `message.send`, whose card names `message:<id>` from the body and binds to the call's arguments, so nothing reaches the lane until a member confirms it, and the confirmed message is the member's, with the delegate as its creation event's proposer. No delegate policy exempts it. The assistant's is the operational `message.send_by_assistant`, which goes at once. A delegate's message whose `id` is not plain, or that a lane could not receive, answers 400 `invalid` before it becomes a card. A message never decides anything: a card or a request stays open whatever a message says.

`POST /v1/projects/{project}/approvals/{id}/decide` and `POST /v1/projects/{project}/questions/{id}/answer` take an optional `place`, `needs_you` or `conversation`. On the web listener, `"place": "conversation"` records the channel `conversation`; otherwise the channel is `web` or `cli`. A member's decision of an approval request records its channel as a card's does, and an answer records it in its decision's event. `POST /v1/projects/{project}/questions/{id}/answer` also takes `supersedes`, the ID of a decision in force the answer replaces, and `no_conflict`, the IDs of decisions its scope overlaps that it does not conflict with. The decision the answer becomes records both, and the decision it replaces ends `replaced` in the same transaction, with no rework. A `supersedes` that names a decision that no longer stands answers 409 `decision_ended`, and one nobody recorded answers 404 `not_found`, and either leaves the question open. `assumed: true` records the answer as an assumption, which closes the question as an orchestrator's rung 4 does; a question whose answer would be one-way refuses it with 403 `one_way` and stays open.

`POST /v1/projects/{project}/questions/{id}/merge` takes `into`, the ID of an open question that stays, and answers 204. It closes the question as a duplicate of that one, with a ladder step that names it, moves every lane attached to it there, and makes the one that stays block when the merged one did. It needs no hold and ends any orchestrator's hold. Only a member with a session calls it: a delegate's call is refused as member-only. A merge into the same question answers 400 `invalid`, and one into a question that no longer waits answers 409 `resolved`. A planning lane's question merges only into another planning lane's question or one that waits for a person; a merge into one an orchestrator could still answer answers 400 `invalid`. A question no orchestrator took within the batch window reaches a batch from the core, and its item states `no_orchestrator: true`; an item states its `ladder_trace` when the question passed a rung, and a question states `asked_at` when the ledger kept it.

`POST /v1/projects/{project}/decisions/{id}/keep` takes no body and answers 201 with the decision it records: the decision the path names, in force, recorded again as the member's, with its status, statement, rationale, citations, scope, reversibility, categories, and the question it answered, under the ID `kept-<id>` (a digest of the ID, under `kept_`, when that would not be an ID), replacing it. It binds nothing anew, so the work the decision reaches stands as it was. It is the member-only operation `decision.keep`: a delegate's call, the assistant's included, answers 403 `member_only`, and no card stands in for it. A second call finds the first and answers with the same decision, a decision the ledger does not hold answers 404, and one no longer in force answers 409 `decision_ended`. Needs you offers it as Keep on a one-way decision an orchestrator made.

`POST /v1/projects/{project}/questions/{id}/decide-now` takes no body and answers 200 with the question as it waits for a person, with its `batch_id`. It is the member-only operation `question.decide_now`: it takes a question still on the ladder off it, ends any hold an orchestrator had on it, adds a ladder step whose `outcome` is `decided_now` and whose `by` is the member, and delivers the batch the question joins at once, with whatever else waited in it. A question that already waits for a person is answered as it stands, and one that no longer waits is refused as resolved, with 409.

Each step of a question's `ladder_trace` holds its `rung`, `outcome`, and `candidates`, and `by`, who worked the rung: an orchestrator by its worker's ID, or a member, and nobody for a rung the core ran. A rung that decided or assumed names its `decision`, with that decision's `rationale`, and its `candidates` are the decision's citations. A rung 1 answer from a decision the record holds names that `decision`, with the outcome `answered`. The ledger writes `by`, `decision`, and `rationale`, whatever a step an orchestrator sends says of them. A member takes over a question an orchestrator holds, on any rung, by answering it, recording an assumption, or merging it: the hold ends, and the orchestrator's next act on that question answers 409 `resolved`, whose message says to drop it.

`POST /v1/projects/{project}/batches/{id}/answers` answers a delivered batch in one request, and only a member with a session calls it: a delegate's call is refused as member-only. It takes `answers`, a list of `{question, id, answer, rationale, citations, supersedes, no_conflict, accepted}`, and an optional `place`, and answers 201 with `decisions`, one for each answer in the order asked. Every answer is recorded in one transaction or none is. A refused answer fails the whole request with the status of its refusal, and its message names the answer's position and its question. `accepted: true` records the question's recommendation as the answer, with the recommendation's rationale and the item's citations, and then `answer`, `rationale`, and `citations` stay empty; any other answer is the member's own and needs a `rationale`. An answer may also carry `expect_reversibility`, `reversible` or `one_way`, the reversibility its item stated when the member read it. When the decision policy in force gives the answer another, the request answers 409 `reversibility_changed`, records nothing, and its message names the answer and which way it changed, such as "answer 2, for question q-2: the answer's reversibility changed since it was read: it is one-way now". Without it, the answer takes what the policy gives. A question the batch does not hold, one listed twice, and a question answered already each refuse the request, and an `id` that an earlier request recorded for the same question finds that decision, so a retry of the whole request records nothing twice. An item of a batch read states `reversibility`, `reversible` or `one_way`, by the rule the answer applies, and `recommendation_rationale`.

The assistant policy is a versioned policy of kind `assistant`, the installation's, published with `POST /v1/projects/{project}/policies` as a member and listed with `GET /v1/projects/{project}/policies?kind=assistant`. `idle_stop` is a duration from one minute to 24 hours, and the built-in version stops an idle session after 15 minutes. `warm_idle_stop`, from one minute to 24 hours and never longer than `idle_stop`, stops a session that no member message has reached since it started, such as one a warm start opened; it is 2 minutes when a version names none. Once a message reaches the session, `idle_stop` holds:

```toml
[assistant]
version = 2
idle_stop = "30m"
warm_idle_stop = "2m"
```

## Lane panes

A member reaches the terminal pane of a lane that runs in one, as the web UI's pane does. The routes name the lane, and follow it to the pane of its current generation. Only a member's session reaches them, so neither a lane nor an orchestrator can read a screen or type into one, and typing into a pane needs the CSRF token, as every change from the web listener does.

| Route | Body | Answer |
|-------|------|--------|
| `GET /v1/projects/{project}/panes/{id}` | | A stream of server-sent events: `screen`, with `lane_id`, `generation`, and `screen`, the visible screen with the escape sequences that set its colours and emphasis, each time it changes; and `lane`, with `lane_id`, `generation`, and `state`, while the lane has no screen to show, such as while it is parked |
| `POST /v1/projects/{project}/panes/{id}/input` | `{"text": "...", "enter": true}` or `{"key": "..."}` | 204 once the pane took the input |

`text` is typed literally, with Enter after it when `enter` is true. It holds at most 4096 bytes and no control character, which would act as a key. Text the worker types into a pane, such as a brief when the socket is unavailable, is cleaned before it is typed, and text sent over the socket, messages included, is not typed and not changed. The cleaning turns a carriage return and line feed pair into a line feed, and every other control character is dropped, the escape, the carriage return on its own, DEL, and the C1 controls among them, so only a line feed and a tab remain. Printable characters in any script are sent as they are, and a trailing semicolon is kept.

`key` is a key sequence:

- A chord is zero or more of `Ctrl`, `Alt`, and `Shift`, each followed by a hyphen, then a named key or one printable character: `Enter`, `Shift-Tab`, `Ctrl-O`, `Alt-x`, or `Ctrl--`, which is Ctrl and the minus key. Modifiers and names are read in any case.
- The named keys are the ones tmux names: `Up`, `Down`, `Left`, `Right`, `BSpace` (Backspace), `BTab` (Shift-Tab), `DC` (Delete), `End`, `Enter`, `Escape`, `F1` to `F12`, `Home`, `IC` (Insert), `PageUp`, `PageDown`, `Space`, and `Tab` ([tmux](https://man.openbsd.org/tmux.1#KEY_BINDINGS)).
- Shift goes only with a named key, such as `Shift-Up`. A character carries its own Shift, so a sequence holds `A`, not `Shift-a`.
- A sequence is 1 to 8 chords, each separated from the next by one space, such as `Ctrl-X Ctrl-S`, in at most 256 bytes.

The server reads each chord into tmux's name for it: Ctrl is `C-`, Alt is `M-`, and Shift is `S-`, so `Ctrl-X Ctrl-S` is `C-x C-s`, with a letter under Ctrl lowercase, as a terminal sends it; `Shift-Tab` is `BTab`. It sends the names with `send-keys`, which looks each one up as a key, and sends text with `send-keys -l`, which looks up none ([tmux](https://man.openbsd.org/tmux.1#send-keys)). Anything outside the grammar answers 400 `invalid`, among them tmux's own spelling such as `C-c`, a word, a control character, a modifier with no key or twice, Shift on a character, and a ninth chord, so no string a page sends reaches tmux as anything but a key it names.

| Status | Code | When |
|--------|------|------|
| 409 | `lane_ended` | The lane has ended, so it will never have a pane again |
| 409 | `no_pane` | The lane has no pane now: it runs without a terminal, its pane has not opened yet, it is parked, or no worker this control plane reaches holds it |

## A lane pane's scrollback

`GET /v1/projects/{project}/panes/{id}/scrollback?lines=N` reads the scrollback of a lane's pane, the lines that scrolled off the top of its screen, and needs a member's session. `lines` is a whole number from 1 to 10000, and 200 without one. It answers `lane_id`, `generation`, `lines`, the newest of the history's lines up to that count, oldest first, each ending in a newline, with the escape sequences that set their colours and emphasis; `size`, how many lines the history holds now; and `limit`, how many lines tmux keeps, its `history-limit` ([tmux](https://man.openbsd.org/tmux.1#history-limit)). A count out of bounds answers 400 `invalid`, an ended lane 409 `lane_ended`, and a lane with no pane to read now, such as a parked one, 409 `no_pane`. `ropeshift lane scrollback <lane> [--lines N]` prints the same lines as plain text, and with `--json` prints this answer.

## Searching a project's records

`GET /v1/projects/{project}/views/search` is the read model the web UI's command palette reads. It lists the project's work orders, lanes, plans, contracts, requirements, decisions, questions, planning documents, and repositories, and the calling member's conversations by name as kind `conversation`, each with its kind, ID, title, and state, and it changes nothing. `q` keeps the records whose ID or title holds every word, in any order and any case: an exact ID first, then an ID that begins with the words, then words that each begin a word of the title, then the rest. `category` names one kind. `limit` caps the list, 20 by default when `q` is set, and `more` says the cap cut it. With no `q`, every record is listed.

## Reading a plan by version, and a planning session's outline

`GET /v1/projects/{project}/plans/{id}` answers a plan with its goal, each contract as the shown version holds it, their work orders, and the request to approve it: the one that waits, or else the newest. `body` is the text of the plan's file at the version the answer shows, the Markdown after its front matter, which the ledger keeps for each version, cut at 262144 bytes with `body_cut` true when it was cut, and absent for a version recorded before the ledger kept it. `versions` lists every version of the plan, newest first, each with its digest and the ID and state of the request that stands for it, and none of those when nobody asked about that version. `?version=N` answers with the request of that version, whatever state it is in, and refuses a version the plan never had with 404 and a version that is no whole number from 1 with 400. A request is read by its own ID with `GET /v1/projects/{project}/approvals/{id}`, which is how a first version of a plan is read before the ledger holds the plan. A later version a planning branch asks about, of a plan the ledger holds, is read from the plan's route as well: its request answers with the drafts its `detail` carries, and with no `records` or `milestones`, which the ledger holds only once the version is approved. The `detail` of a request a planning branch raised carries the version's `body` and `body_cut`, its `goal` with a `title`, a `statement`, and `success_measures`, its `contracts`, each with an `id`, a `title`, a `statement`, and `criteria`, the version's `drafts`, the `manifest` entries of every manifest the version lists, and the `targets`, the repository names its work orders give in `repo`, sorted and once each, because the ledger holds no record of them until a member approves it, and Needs you lists those drafts for it. The plan's view reads `body` from that `detail` for such a version. When the version's manifest lists repositories, the request carries `registration`: while it waits, a preview with `preview` true that a member's session reads, of what approving would register, read from the clones on the daemon's worker's machine with nothing recorded, and for each entry approving would create, from the worker's creator running only the checks that come before a write, which only a member's session reads; once approved, what the approval registered, as it recorded then. The request read by its own ID carries the same, so a first version a planning branch asks about, which has no plan route until a member approves it, previews from the manifest and the work its `detail` carries. Each entry of its `repositories` gives the manifest's `name`, `manifest_path`, and `remote`, the `path` it leads to on that machine, the `outcome` (`registered`, `known`, `refused`, `not_attempted`, or `planned` for an entry with `create` that no work order of the version names in `repo`, for which approving creates and registers nothing, `created` for one that a work order names, which approving creates and registers, and `create_failed` for a creation that stopped at a step), `creation` for an entry to create, with what approving would create, or did, as `POST /v1/projects/{project}/approvals/{id}/decide` describes, and a `reason` for a refusal, a planned entry, or a failed creation, and `problem` says why the preview or the registration fell short. The request also carries `forecast`, the version's forecasts and estimates as `GET /v1/projects/{project}/plans/{id}/forecast` answers them below, with their `state`, so a member reads "forecast pending" before the forecast tick has forecast the version. Approving the version records what that answer holds then as its [baseline](measures.md#baselines).

Approving a plan version with `POST /v1/projects/{project}/approvals/{id}/decide` records each of its draft decisions as the member's decision, under an ID derived from the plan, the version, and the draft, which starts with `pd-`. No other writer names a decision under that prefix, but a ledger may hold one recorded before that held. A decision under a derived ID is the approval's own only when a member recorded it and it cites the plan version, as approval records it. When a decision holds a derived ID of the version with other content, or holds it with the same content but is not the approval's own, or is in force under the ID an earlier version derived for a draft and is not that approval's own, the approval answers 409 `decision_clash`, naming each such decision, who recorded it, and its draft, and records nothing: the request stays pending. Overturning a decision under the version's own IDs changes its status, so the clash stays, and a new version of the plan derives new IDs for its drafts; a decision in force under an earlier version's ID holds every later version until a member overturns it. The approval's own decision with the same content is the same answer, and the approval goes on, and an earlier version's own decision of a draft that did not change carries forward. A draft whose earlier decision a decision recorded outside the plan replaced or overturned is not decided again while its text is unchanged: the request's `replaced` lists it with the earlier decision, how it ended (`status`), and the decision in force (`in_force`, `statement`), and the version's page in `GET /v1/projects/{project}/plans/{id}` lists the same. A draft whose text changed is decided under the new version's ID, and the decision it records supersedes the decision in force. A planning branch a member approved before intake read it, whose draft would clash, asks for approval again once intake records its version, and that approval names the clash. The approval also records in the request's `detail`, as `shown.ids`, the decisions the plan's open revision listed when the member approved, and an empty list when it listed none. Those are the decisions the approval showed: the revision it closes lists them, and a decision recorded after it never joins them, whatever time it carries. A request approved by an earlier release has no `shown`, and its revision splits at the time it was approved.

`POST /v1/projects/{project}/approvals/{id}/repositories/{name}/retry` runs the creation of one repository an approved plan version names again, as one entry of a real run under that approval, with the key of its first run, and appends the approval's registration as the last one with that entry replaced; an approval that recorded no registration, or whose record holds the problem that stopped its run, such as a creator that could not answer, runs the whole registration again, under the registration's lock, leaving out each entry a member skipped. `POST /v1/projects/{project}/approvals/{id}/repositories/{name}/skip`, with `{"reason"}` of 1 to 2000 characters, leaves the repository uncreated: it records `approval.repository_creation_skipped` and a registration with the entry `skipped`, and the work orders that name the repository stay in contract review. Both answer 200 with the approval as `POST .../decide` does, with the `repositories` its registration holds now and, when a run met an error after it began, `repositories_problem`. Both answer 409 `illegal_move`, naming why, when the approval is not an approved plan approval, the entry is not one the approval's version creates, the project holds the name, a member skipped the entry ("skipped; a later approved version that targets it creates it", which a retry never undoes), or its creation runs now ("api is being created now"), 400 `invalid` for a reason outside 1 to 2000 characters once trimmed, or with a control character or a line break, which is kept as one plain line, 404 for an approval nobody holds, and 403 `member_only` for a delegate, an orchestrator, and the assistant: only a member's session retries or skips a creation. A retry runs on the daemon's worker, and a client that disconnects does not stop it. A retry has the 10 minute limit of an approval's run.

A repository an approved plan version creates whose creation was refused, failed, or was interrupted, and whose name the project does not hold, is one item of the project's `needs-you` view, of kind `repository_creation`, with the ID `<approval>/<name>` and the time of the creation's latest record. A creation skipped or created is not listed, and neither is one a check refused because another creation holds its path, which says to read the preview again. Its `repository_creation` holds the `approval`, the `plan` and `plan_version` it belongs to, the entry's `name`, its `manifest_path`, the `path` it leads to on the daemon's worker's machine, the `state` (`refused`, `failed`, `interrupted`, or `running`), the `reason` it stopped, the `remedy`, which is what a member does about it besides Retry and Skip when something can be done, the `creation` it made as far as it came, and the `actions`, `repository_retry` and `repository_skip`, which are `ropeshift plan retry` and `ropeshift plan skip`. A creation a retry's check refused after its latest record, such as one that finds the forge repository there because a create timed out after the forge made it, is `refused` with that reason, and its `remedy` says to clone the repository where the entry's path leads and write `remote` in place of `create` in the manifest entry, or to skip it; another refusal's `remedy` names the command its check gave. A creation that runs in the daemon now is `running` and has no action or remedy; one whose latest record is a start with no finish, and that runs in no process, is `interrupted`.

`GET /v1/projects/{project}/lanes/{id}` reads a lane with its state, conditions, liveness, reachability, and freshness, as `GET /v1/projects/{project}/lanes` lists them and the `shop-floor` view gives them. While the lane's worker probes the agent CLI version the lane's process runs ([qualification](qualification.md)), the lane carries `checking`, with the `driver`, the `version`, and `words`, which say what the check means for the lane and what ends it, such as `Checking Claude Code 2.1.400: this lane runs on documented surfaces until the check passes; a respawn then picks up the qualified surfaces`. `checking` is absent once the probe ends, and on a lane that ended or is parked. A lane whose process started on the surfaces the release's shipped qualification matrix holds for the version carries `surfaces` as `matrix`, and the words of its `checking` read `Checking Claude Code 2.1.317: this lane runs on the surfaces this release qualified for 2.1.317 until the check ends`; `surfaces` stays after the check ends, and it is absent unless the process's surfaces came from the shipped matrix, so it is absent for surfaces a probe qualified and for documented surfaces alike. `condition_notes` holds the sentence of each of the lane's conditions that has one, worded by the server, so `degraded_mode` reads `Runs on documented surfaces until it restarts on a qualified version.` and, for a lane whose `surfaces` is `matrix`, `Runs on the surfaces this release qualified for its version until it restarts on a qualified version.` A worker's status whose `checking` names a driver or a version in no usual shape, or whose `words` run past 300 bytes or are not one line of plain text, is kept without it.

`GET /v1/projects/{project}/lanes/{id}/outline` reads the plan a planning lane has committed to its branch, at the branch's tip now, in the checkout of the machine the daemon runs on, and compares it with the commit the lane's branch began at. Once the lane's work order is done, it reads the commit a member accepted instead, which a later commit on the branch does not move and which stays readable once the branch is deleted. It lists the planning documents added or changed since then, each with its path, kind, and title; the milestones with their priorities; the contracts with their criterion and work order counts; the draft decisions; the work order's questions nobody has answered, with the blocking ones marked; and the request to approve the plan that stands for the tip, with its `id`, `state`, `version`, and the `plan_id` of the plan it belongs to once the ledger holds one, or, when none does while a blocking question is open, why the version is not submitted. A branch it cannot read, because the lane runs on another machine or has no commit yet, answers `unread` with the reason and nothing else. A lane that is not a planning lane's is refused with 400. `ropeshift lane outline <lane>` prints the same.

`GET /v1/projects/{project}/plans/{id}/forecast` answers the latest forecasts the forecast tick kept for a plan's newest version, or with `?version=N` for that version: `plan_id`, `plan_version`, `state`, `forecasts`, the plan's own first and then each milestone's by ID, and `estimate_set`, the estimate set they were made from, with every work order's estimate. `state` says whether the tick has forecast the version: `forecast` once it has; `pending` until it has, which every surface reads as "forecast pending", because the tick forecasts a version intake recorded within one tick and nothing forecasts on a request; or `superseded` for a version a newer one replaced before the tick forecast it, which it never will, because the tick forecasts only each plan's newest version. Until the tick has forecast the version, `forecasts` is empty and `estimate_set` is the version's newest set, which is null for a version with no open work; once the tick has forecast a version with no open work, `estimate_set` is null too, because its forecasts rest on no estimate. Each forecast carries its `id`; the `plan_id` and `plan_version` it forecasts; its `milestone_id`, absent for the plan's own; the `estimate_set_id` of the set it was made from, absent when it rests on none; its `status` (`forecast`, `no_history`, `no_capacity`, or `finished`); `end_p50` and `end_p85`, epoch milliseconds, and `cost_p50_usd` and `cost_p85_usd`, estimated at list price, which only `forecast` has; the what-ifs `end_p85_cap_plus_one` and `end_p85_person_median`; `confidence`, `low_confidence_work_orders`, `left_out`, `outside`, and `lower_bound` (`none`, `p85`, or `all`, where an absent one is `none`); the `explanation` every surface shows; and what makes it again: `seed`, `trials`, `cap`, where zero caps nothing, `ledger_rev`, `as_of`, `person_median_ms`, `policy_version`, and `inputs_digest`, with `created_at` and `day`, the UTC midnight it counts toward. A plan with no version yet, and a version the plan never had, answer 404, and a version that is no whole number from 1 answers 400. `ropeshift plan forecast` prints the same.

In the documents view, each work order that carries a traced criterion has a `verdict` for that criterion: the latest verdict that speaks for the work order's current attempt and the commit it left, with its outcome and the commit it read. A criterion no review has judged has none.

## The plane protocol

One worker per machine serves every active project. Version 2 of the plane protocol names the project on every lease, claim, desired-state item, and uploaded event, and on every call a lane or an orchestrator makes through its worker. Desired state lists each project the worker serves with its fleet mode, and the revision of each beside the installation's own, and a worker reads it again when any of them moves. An archived project takes no claim and is offered nothing.

A worker claims work on its own route, `POST /v1/workers/{id}/claims`, with the work order and its project in the body.

`GET /v1/workers/{id}/caps` reads a worker's lane caps: `max_lanes`, null where it follows the recommendation and 0 for no cap, `max_lanes_per_sign_in`, 0 for no cap, `effective_max_lanes`, the cap in force, and the `recommendation` the worker last reported, with the numbers behind it and its `reason`. `PUT /v1/workers/{id}/caps` takes `{"max_lanes": N, "max_lanes_per_sign_in": N}` and needs a member's session. A value is any number from 0, with no upper bound, and a `max_lanes` that is null or left out follows the recommendation. The caps live in the user's profile of the worker's machine, which the change edits in place, so the file and the API are one setting. The answer is the caps as they now stand, and carries a `warning`, with the `recommended` value and its `reason`, when `max_lanes` is above the recommendation; the value is saved all the same. A worker that does not run on the daemon's own machine answers 400 `invalid`, because its caps are in the user's profile on that machine. Setting them is member-only: a delegate's call answers 403 `member_only`.

Every heartbeat records on the worker's record when its session last beat, by the control plane's clock and with no event, and a worker that opened its session or beat within three heartbeats is connected. A beat the control plane cannot record fails nothing else: the heartbeat still renews and fences the worker's leases, and the next beat records it.

A heartbeat carries a `report` when the worker has measured since its last answered heartbeat: its machine, each session's process tree, the lane cap it recommends with the numbers behind it, the caps in force, `running_lanes`, the lanes that hold a place under those caps as admission counts them, and the warnings past its thresholds. The control plane keeps the last report on the worker's record, with no event, as `report` and `reported_at`, dated by its own clock less the report's `age_ms`, held between 0 and the window the report stays observed, and never before the session opened or before the worker's last `reported_at`. A report it cannot keep fails nothing else: the heartbeat still renews and fences the worker's leases, and its answer carries `report_error`, so the worker sends the report again. A report is the worker's word, so the control plane keeps at most 512 sessions, 64 warnings, and 64 volumes of it, each text cut at 1024 bytes, and its interval between a second and a day; a report still larger than 256 KiB is not kept. A measure the machine cannot provide is absent from the report, never zero. `GET /v1/workers` lists each worker with its last report, and `as_of`, the time of the read. Each worker of a project's `shop-floor` view carries the same, and its `drivers`, the doctor's result for each driver its manifest names: `usable`, by the rule an offer applies, and for a driver that is not, `word` (`absent`, `unusable`, or `signed out`), `reason`, and for a CLI that failed its version check, `fix`. A worker whose manifest names no driver has none. Its `orchestrator`, as `GET /v1/workers/{id}/orchestrator` answers it, is the ledger's record with `waiting_for`, what holds a run a member wants before its session starts, which the control plane reads at the time of the read and no event holds. A worker starts the session only when there is something to judge, and until then its lane carries the condition `awaiting_wake`, which it drops the moment a wake arrives, before it prepares the session. While it carries it, `waiting_for` is `run_window` on an attended worker with no run window open, because such a worker's wake holds no new work, and `work` on any other worker. It is absent otherwise, including while the session is prepared after a wake. `PUT /v1/workers/{id}/orchestrator` answers with the orchestrator as this read gives it after the change. A report carries `sign_in`, what the worker knows of its sign-in's usage limit: `limited` while the limit holds, until its reset or, with none reported, until a probe finds it gone; `window`, `five_hour` or `seven_day`; `resets_at_ms`, the vendor's reset; `used_percentage` with `used_known`; and `read_age_ms`, how long before the report the worker last heard. The control plane refuses a report whose `resets_at_ms` is negative, holds `read_age_ms` between 0 and seven days and `used_percentage` between 0 and 100, and reads a `window` other than `five_hour` or `seven_day` as none. Each worker of `shop-floor`, and `GET /v1/workers/{id}/orchestrator` as `hold` and `scheduled`, carry `orchestrator_hold`, what keeps its orchestrator from starting or running now, and `scheduled_start`, a start a member scheduled for its sign-in's reset; each is absent when there is none. `reason` is `offline` for a worker not connected within a few heartbeats, `tripped` for a breaker that stopped it, or `usage_limit` with `window`, `resets_at`, `read_at`, and `stale`, which says the reset passed while the limit held or was read longer ago than its window lasts.

`POST /v1/workers/{id}/orchestrator/schedule` schedules the start of the worker's orchestrator for its sign-in's reset, and answers 201 with the start: `worker_id`, `starts_at`, absent while it waits for the next reported reset, `scheduled_by`, `scheduled_at`, and `missed`, the resets that passed with the limit holding. A sign-in that is not at its limit answers 400 `invalid`, and only a member with a session calls it: a delegate's call is refused as member-only. A tick moves each start. A report that says the limit is gone starts the orchestrator as the member who scheduled it: before the reset, when the limit ended early, or after it, at the first report since. A report after the reset that says the limit still holds moves the start to the reset reported since, or leaves it waiting for the next. A report with no `sign_in`, as a worker of an earlier build sends, leaves the start waiting, and once it waits so, it starts at the first report that says the limit is gone. A start for an orchestrator already asked to run ends with nothing done, and one whose breaker tripped since leaves the breaker tripped. A stop of the orchestrator ends its scheduled start. The schedule answers 400 `invalid` for an orchestrator already asked to run or whose breaker tripped. `DELETE /v1/workers/{id}/orchestrator/schedule` cancels it and answers 204, or 404 `not_found` when none is scheduled. `report_freshness` says whether the report is `observed`, from within three of its intervals or heartbeats, whichever is longer, or `last_reported`. A claim is held to the per-worker cap the last report states, so a change to the cap takes hold without a new session, and to the capacity the session opened with before the first report. From each report the control plane also records when the worker's running lanes reach `max_lanes` or `max_lanes_per_sign_in` and when they fall below it, as described in [capacity intervals](measures.md#capacity-intervals).

Version 3 adds the assistant's sessions. Desired state's `assistants` lists each running conversation placed on the worker, with its project, conversation, member, run lane, the conversation's generation the run began at, the assistant policy's idle stop, whether it begins with an empty context, the compactions asked of it, and its messages. Each start names a run lane of its own, and the worker runs every start of a conversation in one directory of its own, so a start resumes the vendor's session where it last ran. A resume the vendor refuses starts a fresh generation whose first prompt holds the conversation's newest entries, and the refused session is not tried again. Desired state's `forget` lists each deleted conversation the worker ran, with its project, conversation, and run lanes and no text; once none of those runs goes on, the worker removes the messages to it and its runs' records from its journal and the conversation's directory, and uploads `assistant_forgotten` with the conversation, after which `forget` names it no more. The worker asks `POST /v1/workers/{id}/assistant-credentials`, with the project, conversation, run lane, and the run's generation, for each generation it starts, and the answer holds the credential's token once, with the project's facts and the conversation's newest 50 entries since its last clear for the session's first prompt. It records each reply with `POST /v1/workers/{id}/assistant-entries`, under the vendor message's ID, so a retry records it once. Uploads from an assistant's run carry no work order, and its run's states move its conversation. A worker whose session was opened on version 2 is told of no assistant.

Version 4 adds the delegate that sent a lane's own profile layer. A desired lease's `delegated` names the delegate, `<member ID>/<credential ID>`, the `policy_version` of the delegate policy in force when it started the lane, and `restricted`, true when that version sets `raise_model_and_effort = false`; the worker holds the lane's overrides to it ([authorization](authorization.md#delegates)). A lease a member, an orchestrator, or the system started has none. An older worker would drop `delegated` and run the overrides unrestricted, so a worker on version 3 is offered a lease whose `delegated` is restricted as its claim with no lane: it keeps and renews the claim and starts nothing, and the lane starts once the worker is upgraded and opens a session on version 4. Every other lease reaches it whole. The control plane accepts a worker one version behind its own, so a worker on version 3 can no longer open a session, and a worker whose session an earlier build opened on version 3 keeps it until it opens another.

Version 5 adds template writes, which let a member start a project from the web UI ([the dialog](web-ui.md#start-a-project-from-a-template)). Desired state's `template_writes` lists each request that names the worker, that it has not reported, and that has not expired, each with `id`, `shape` (`workspace`, `monorepo`, or `repository`), `path`, `name`, `project`, `repositories` (each with `name` and `remote`, for a workspace), `first_commit`, and `expires_at`, in Unix milliseconds. The control plane lists a request only for the worker it names, only while that worker's session speaks version 5 or newer, and only until `expires_at`, which is two minutes after the request was made. The control plane serves the current version and the one before it, so a worker on version 4 is no longer served. The worker writes the shape's files and reports with `POST /v1/workers/{id}/template-reports`, which takes the worker's credential and is served on the socket and on a group server's network listener, never on the web listener's list. The body holds `request`, `outcome` (`written` or `refused`), and for a refusal its `reason` and `detail`, and for a write `project`, the name rendered into the files, `files`, each path of the shape relative to the folder and sorted, `left`, the paths among them that the folder held before the write and the write left as they were, `commit`, the first commit's ID when it made one, `commit_error`, what git said when the commit failed, `clone`, whether the folder is the top of a clone that holds a commit after the write, and `commands`. The first report of a request is recorded and a later one is answered as accepted and changes nothing. A report after `expires_at` is still recorded, because the files exist.

A member asks for a template write with `POST /v1/workers/{id}/template-writes`, which needs a member's session and the CSRF token on the web listener, and which a delegate's call refuses as `member_only`. The body holds `shape`, `path`, `repositories`, `name`, `project`, and `first_commit`. `name` is the project's name rendered into the files and into the commands that register them, on any shape, and the folder's name makes one when it is absent. The daemon refuses it as `invalid`, and records nothing, for a shape other than the three; a `path` that is not absolute, that holds a `..` element as sent, or that is not in its clean form, with a trailing slash, `//`, or `/./`, which would reach a symbolic link through a spelling no check of the link sees; a `path` at or inside the state, run, or worktree folder of the daemon, when the worker is the one the daemon runs; `repositories` on a shape other than `workspace`, a name a repository cannot have, a name given twice, or an empty or unsafe remote; a `project` on a shape other than `repository`, or one that is no project name; a `name` that is no project name; a folder whose name makes no project name, when the request gives no `name`; a `name` for a worker whose session speaks a version older than 7, with the message "worker NAME speaks protocol N; upgrade it to name a project from the web UI"; a worker that is not connected; and a `remote`, `new`, `url`, or `create` for a worker whose session speaks a version older than 6, with the message "worker NAME speaks protocol N; upgrade it to create a project's remote". An unknown worker is `not_found`. It answers 202 with the request. `GET /v1/workers/{id}/template-writes/{request}` needs a member's session, as the request does, and a delegate's call refuses as `member_only`, and it answers the request: `id`, `worker`, `requested_by`, `requested_at`, `expires_at`, the fields it was made with, its `state`, `report` with the worker's report once there is one, `reported_at`, and `registrable`. The state is `offered` until the worker reports, then `written` or `refused`, and `expired` for a request nobody reported by `expires_at`. `registrable` is true when the report says `clone` and the worker is the one this daemon runs, because the register route reads clones only through that worker's checkouts. Creating a request and reporting one each append an event to the installation's log, `template_write.requested` and `template_write.reported`, which name the member, the worker, the shape, and the folder.

Version 6 adds a new project's remotes. A template write's body gains `remote`, the remote of the folder's own repository: absent for none, `{"url": "<remote>"}` to add a URL as `origin`, or `{"create": {"forge": "github", "owner": "<owner>", "visibility": "private"}}` to create the repository on GitHub, where `visibility` is `private` or `public` and absent is `private`. Each entry of `repositories` gains `new`: a new entry is written at `repos/<name>` from the repository shape's files, gets its own first commit, and takes an optional `url` or `create` of the same form, at most one, while an existing entry keeps its required `remote`. The daemon refuses as `invalid`, before it records anything, a `remote` with both or neither of `url` and `create`; a `url` that is empty, holds whitespace, starts with a dash, or is not a one-line git remote; a forge other than `github`, with "creating a repository on FORGE is not supported yet; ropeshift creates repositories on GitHub"; an owner that is not a GitHub account name (letters, digits, and single hyphens, at most 39 characters, not starting or ending with a hyphen); a `visibility` other than the two; any remote with `first_commit` false, because a remote needs a commit to push; and `new` on a shape other than `workspace`. The GitHub repository's name is the folder's base name for the folder's own repository and the entry's name for a code repository.

Before it writes anything, a worker that is to create a repository checks, in order, that `gh` is on its `PATH` (`gh_missing`), that `gh auth status --hostname github.com --json hosts` answers (`gh_outdated`) and shows an active, valid account (`gh_signed_out`), that a classic token holds the `repo` scope, or `public_repo` when every created repository is public (`gh_scope_missing`), that each owner is the account or one of its organizations (`owner_not_available`, or `gh_scope_missing` when the token cannot list organizations), and that no repository exists at each owner and name (`remote_exists`). The first failing check ends the request as `refused` with its `reason`, its `detail`, and in `remedy` the command the person runs; nothing is written and nothing is created. A folder that a clone the worker does not make holds is refused as `remote_needs_repository`. After the files and the first commits, the worker gives each repository its remote in three steps, each limited to two minutes and run without a prompt: `create` (`gh repo create <owner>/<name> --private`, or `--public` only when asked), `origin` (`git remote add origin <url>`), and `push` (`git push --set-upstream origin -- <branch>`). A repository created over `https` pushes with `gh` as git's credential helper for that one command. A failed step marks the later steps of that repository `skipped`, and the worker goes on to the next repository; nothing local is removed and a created repository is never deleted. The report gains `repositories`, one for the folder's own repository (`path` `.`) and one for each new code repository (`repos/<name>`), each with `name`, `path`, `commit`, `commit_error`, `remote`, and `steps` (`step` `create`, `origin`, or `push`, `outcome` `done`, `failed`, or `skipped`, and `detail`), and `remaining`, the commands that finish what did not run. The worker journals each step before and after it runs, and checks a step it finds started before it runs it again, so a crash creates nothing twice and reports once. Each repository the report records as created appends one installation event, `repository.remote_created`, naming the member, the worker, the forge, the repository, and the visibility.

A member asks a worker to read its GitHub account, to choose an owner, with `POST /v1/workers/{id}/forge-account-reads` and the body `{"forge": "github"}`, which needs a member's session and the CSRF token and which a delegate's call refuses as `member_only`. It answers 202 with the request, and `GET /v1/workers/{id}/forge-account-reads/{request}`, which needs a member's session and which a delegate's call refuses as `member_only`, because its report names the account's login and organizations, answers its `state`, `offered`, `reported`, or `expired`, and `report` once the worker has reported. Desired state's `forge_account_reads` lists each request that names the worker, that it has not reported, and that has not expired, two minutes after it was made, each with `id`, `forge`, and `expires_at`, and only while the worker's session speaks version 6. The worker runs the first three checks above, the scope check passing with either `repo` or `public_repo` because the visibility is not chosen yet, and reports with `POST /v1/workers/{id}/forge-account-reports`, served on the socket and on a group server's network listener, never on the web listener: `state` (`ok`, `gh_missing`, `gh_outdated`, `gh_signed_out`, or `gh_scope_missing`), `login`, `git_protocol`, `owners` (the login first, then the organizations, sorted), `detail`, and `remedy`. The web listener serves the two member routes, and the worker's report route stays on the socket and the network listener.

Version 7 adds practices checks, which ask a worker that keeps a repository's checkout to run the practices check on it. Desired state's `practices_checks` lists each request that names the worker, that it has not reported, and that has not expired, 30 minutes after it was made, each with `id`, `project`, `repository`, `base_branch`, `binding` (`HOST/OWNER/REPO`, absent for none), `merge_authority`, `scanned_from`, the commit the repository's last completed secret scan read, absent for a scan of the whole history and absent when that scan matched with another version of the credential rules than the control plane's, and `expires_at`, in Unix milliseconds, and only while the worker's session speaks version 7 or newer. A worker on version 6 is still served and is offered none. The worker runs the check on one request at a time against its checkout and reports with `POST /v1/workers/{id}/practices-reports`, which takes the worker's credential and is served on the socket and on a group server's network listener, never on the web listener. The body holds `project`, `request`, `outcome` (`checked` or `failed`), for a failure its `detail`, one line of at most 2000 bytes that names no path of the worker's machine, and for a check its `result`, which must be of the request's repository. The control plane clips each reason and detail of a result to one line of at most 2000 bytes, clips a finding's `id` longer than 2000 bytes to 2000 bytes that end in a digest of the whole `id`, keeps at most 200 secret findings and says `truncated` when it left some out, and refuses a result that holds a practice, a status, or a severity the tables do not hold, or that does not hold each practice of the table exactly once. A result one table version behind the control plane's may lack the practices the current version added, and always holds `secrets`; a result any older holds the whole table. A worker reports a result the control plane refuses as a failed check whose `detail` gives the reason, and sends a result it journaled and could not send whatever desired state lists, so a report after `expires_at` still arrives. The first report of a request is recorded and a later one is answered as accepted and changes nothing. A report after `expires_at` is recorded all the same, because the result is true. A checked report keeps the result as the repository's latest, unless a request made after this one has reported already, and appends the event `practices.checked` with the whole result as it is kept. A result of an incremental secret scan keeps the `secrets` findings of the result it continued from when it continued from where the last completed scan ended, with the credential rules in force. When it did not, the commits between were read by no scan, so its `secrets` read `unknown` unless it found a secret or the kept result held one, and the `secrets` findings of the kept result stay in it, and a result whose secret scan could not run likewise keeps the `secrets` findings of the result it continued from, reading `finding` when it holds any, with the reason the scan failed, and clears the scan's starting commit, so the next check reads the whole history. The version of the credential rules the result's scan used is kept with that commit. A failed report appends `practices.failed` with the detail and keeps the previous result. Version 7 also adds a template write's `name`, which a worker renders into the files in place of the folder's name, so a worker on an older version is offered no request that holds one.

The control plane asks, for each repository, only a connected worker that keeps a checkout of it and speaks version 7, the daemon's own worker first and then the others by name. In solo mode the daemon's own worker is the only one that reports the checkouts it keeps, and a group server does not place a check on any worker yet: it answers every request with the reason "no connected worker keeps a checkout of NAME" and offers no worker a check. A repository with no connected worker that keeps a checkout gets no request, with the reason "no connected worker keeps a checkout of NAME", and one whose connected workers all speak an older version gets none, with the reason "worker NAME speaks protocol N; upgrade it to run the practices check". One request per repository is open at a time, so a request for a repository that has one answers the open one. Making a request appends `practices.requested`, which names the repository, the worker, and the cause: `registration`, `planning_session`, or `member`. A request that no worker reported by its expiry is stored as expired on the next pass of the control plane's tick, with the event `practices.expired`. Each repository a registration makes, whether by `repository add`, by adoption, or from a manifest, including the one a plan's approval registers, gets a request with the cause `registration` once its registration is recorded and its checkout is kept. A repository the project already held and a dry run get none, and a request that is refused or fails changes nothing about the registration; a failure is written to the daemon's log.

A desired lease of a planning work order, a planning session's or an adopt session's, also carries `practices`, which a lease of any other kind lacks: one entry for each active repository of the project, by name, with its `repository`, `name`, and `checked`, which is false for a repository no check has reported, an entry that holds nothing more. A checked entry holds the latest result's `commit` and `age_ms`, in milliseconds as of the read, its `open` findings, at most 50, the most serious first and then by `id`, each with `id`, `severity`, `detail`, and the `fix` of its practice, and `more`, the count of those left out, its `acknowledged` findings, at most 50 by `id`, each with `id` and the member's `reason`, with `more_acknowledged` counting those left out, and its `unknown` practices, at most 50 by `practice`, each with `practice` and `reason`, with `more_unknown` counting those left out. An entry whose result or acknowledgements the control plane could not read holds `unreadable` true and nothing more, and the control plane still serves the lease. A worker puts it in the planning lane's first prompt. A worker that does not know the field ignores it, so it needs no protocol version, and nothing a worker or the control plane decides reads it.

A worker that speaks version 1, which names no project and serves only the first project, is no longer served. Opening a session at version 1 answers 426 with the code `protocol`, and the message says the version is no longer served and the worker must be upgraded; the error also carries the worker's version and the oldest and newest the control plane accepts. A worker whose session was opened at version 1 before the control plane was upgraded is refused the same way on its next call, until it opens a session at version 2.
